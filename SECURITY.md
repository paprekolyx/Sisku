# Политика безопасности Sisku (черновой макет)

**Версия документа:** 0.19.0-draft · 09.10.2026
**Статус проекта:** демонстрационный макет. Ниже — что защищено уже сейчас,
а что отсутствует сознательно и почему (культура «честных границ» унаследована
из учебного проекта).

---

## 1. Какие данные где хранятся

| Данные | Где | Доступ |
|---|---|---|
| Товары, варианты, категории, бренды | Supabase (проект `sisku-draft`) | чтение публично (anon); запись — draft-политики anon-CRUD (baseline 02; исторически скрипты 11–16 — админка без серверного API, см. §2/§3); удаление товаров запрещено by design — только деактивация |
| Тексты `site_content` | Supabase (проект `sisku-draft`) | чтение публично (anon); запись — политика `draft_anon_update_site_content` (baseline 02; исторически скрипт 12): админка «Управление → Сайт». Формулировка «запись только владельцу через SQL Editor» устарела с v0.9.0 (фикс F04) |
| Черновые администраторы: ФИО, e-mail, мессенджер, роль, хеш пароля | таблица `admin_users` | чтение и запись для anon (черновик) — **включая колонку `password_hash`**: SHA-256 без соли от слабых паролей дешифруется мгновенно (фикс F25, см. §3); пользователи вымышленные |
| Промокоды: код, скидка, сроки, лимиты | таблица `promo_codes` | чтение и CRUD для anon (черновик, страница «Управление → Промокоды»); **применение скидки — только серверными функциями** `check_promo`/`create_order` |
| Каталог и справочники: товары, варианты, категории, бренды, способы оплаты/доставки, комплекты (looks, look_items), токены брендбука (brand_colors, brand_templates) | соответствующие таблицы | чтение публично; запись для anon открыта черновыми политиками (baseline 02; исторически скрипты 11–14 — CRUD из админки без серверного API) |
| Заказы: имя, телефон, e-mail, адрес, состав, суммы, фактические скидки (promo_discount, look_discount) | таблица `orders` и связанные | **чтение открыто для anon — осознанное упрощение черновика** (админка без пароля); создание — только через `create_order()` |
| Клиентская база (v0.13.0): ФИО, телефон, e-mail, адрес, комментарий менеджера | таблица `clients`, связь `orders.client_id` | чтение/запись для anon открыты черновыми политиками (baseline 02; исторически скрипт 15) — **только тестовые данные**; контакты в админке маскируются до раскрытия «глазиком»; история имён и контактов (v0.18.0, `client_name_history`/`client_contact_history`, скрипт 28) — RLS без анонимных политик, доступ только через SECURITY DEFINER RPC; в боевой версии — серверный API с ролями и хранение в РФ |
| Справочники оплаты/доставки | `payment_methods`, `delivery_methods` | чтение для anon — все строки (v0.14.0: иначе админка не могла бы управлять отключёнными способами); витрина и заказы используют только активные — `create_order()` проверяет `is_active` на сервере |
| Возвраты (v0.16.0): причины, заявки (заказ, причина, комментарий покупателя), признак «деньги возвращены» и реквизиты чека возврата | `return_reasons`, `return_requests` | чтение — anon (черновое упрощение, как заказы: админка без пароля); **запись заявок — только через security definer RPC** (`create_return_request` — с серверной валидацией номера заказа и кода подтверждения, `admin_set_return_status`, `admin_set_return_refund`), прямых политик записи заявок нет; справочник причин — draft-политики insert/update («Управление → Справочники»), **без DELETE** — удаление только деактивацией; комментарии заявок — только тестовые данные (общее правило черновика) |
| Секретный ключ Supabase (`service_role`) | нигде | в репозиторий и в браузер не попадает никогда |
| Публичный ключ Supabase (anon) | `assets/js/config.js` | штатно публичен: доступ ограничивает RLS |

**Правило черновика: никаких реальных персональных данных.** Тестовые заказы
создаются только с вымышленными именами и контактами: база находится вне
Российской Федерации, хранение реальных ПДн в ней нарушило бы 152-ФЗ.
Боевая версия поедет на российском решении с полной политикой ПДн.
Юридические документы черновика (privacy.html, offer.html) — шаблоны первой
версии: плейсхолдеры [указать: …], плашка о черновом статусе и тестовых данных;
финальные формулировки и чекбоксы согласий — в боевой версии.

## 2. Действующие меры защиты

- **Резервирование и карантин:** остаток списывается при создании заказа;
  `admin_set_status()` возвращает остатки при отмене, а с v0.16.0 (v4,
  фикс F51; исторически скрипт 23 — ныне baseline 03) при «Возврате» единицы уходят НЕ в продажу,
  а в карантин `product_variants.quarantine_qty` («требует осмотра») —
  вернувшийся товар нельзя продать до осмотра (`admin_resolve_quarantine`:
  «вернуть в продажу» / «списать», `FOR UPDATE` на варианте, количество —
  не больше карантина). Строка заказа блокируется `SELECT … FOR UPDATE`:
  две параллельные отмены не возвращают остаток дважды (v0.14.0, фикс F01).
  Скидки промокодов и комплектов пересчитывает только сервер.
- **Цены и остатки считает сервер.** Заказ создаётся только функцией
  `create_order()`: присланные браузером суммы игнорируются, проверяются
  активность товара и остаток варианта, всё пишется одной транзакцией
  (заказ, позиции со снапшотами, доставка, история статусов, клиент,
  скидки). С v0.14.0 функция (v6) дополнительно: клиент создаётся UPSERT-ом
  (параллельные заказы одного нового покупателя не роняют заказ ошибкой
  23505 — фикс F02); строка промокода блокируется, лимит использований
  перепроверяется под блокировкой и инкрементируется условно (фикс F03);
  дубли варианта в корзине схлопываются, списание остатка условное
  (`WHERE stock >= qty`) с читаемым сообщением (фикс F08); итог заказа
  не может стать отрицательным — `greatest(…, 0)` + констрейнт
  `orders_total_nonneg CHECK (total >= 0)` (фикс F07); блокировки строк
  берутся в детерминированном порядке — параллельные заказы не дают
  deadlock (фикс F23).
- **Валидация и анти-спам:** имя обязательно, телефон или e-mail обязателен,
  количество 1–99, не более 50 позиций, не более 3 заказов за 10 минут
  с телефона/e-mail — телефон сравнивается нормализованным ключом
  `draft_phone_key()` («+7 999…» и «8999…» — один человек, фикс F17);
  honeypot-поле против ботов; блокировка повторной отправки формы на время
  запроса; промокод перевалидируется на сервере при каждом изменении корзины
  (фикс F30).
- **Запись бизнес-логики заказов и возвратов — только через security definer
  функции** (`create_order`, `admin_set_status`, `admin_set_paid`,
  `check_promo`; с v0.16.0 — `create_return_request`,
  `admin_set_return_status`, `admin_set_return_refund`,
  `admin_resolve_quarantine`):
  суммы, скидки и остатки браузер не считает и подменить не может.
  **Каталог, справочники, промокоды, луки, брендбук и клиенты при этом
  открыты для анонимной записи draft-политиками (baseline 02; исторически
  скрипты 07–16)** — это
  сознательная граница черновика без серверного API (полный перечень — §3;
  фикс F04: прежняя формулировка «запись из браузера закрыта полностью»
  противоречила фактическим политикам и устарела с v0.4.0).
- **Статусная модель защищает от бессмысленных переходов:** смена статуса
  только через `admin_set_status()` с проверкой таблицы `status_transitions`;
  оплата — отдельный признак `is_paid` + дата, а не статус.
- **XSS (v0.14.0 усилено, фикс F05/F06/F24):** все данные из базы и введённые
  пользователем экранируются общей утилитой `esc()` (`assets/js/util.js`);
  ссылки (`href` из `site_content`, `messenger_url`) проходят whitelist схем
  `safeUrl()` — `javascript:`, `data:` и protocol-relative отклоняются,
  а строка предварительно очищается от управляющих символов и пробелов
  (v0.14.1, ревью N1 — закрыт обход вида `java\tscript:`);
  значения брендбука валидируются как `#rrggbb` до вставки в атрибуты;
  CSV-экспорты экранируют значения, начинающиеся с `= + - @ TAB CR`
  (защита от формул-инъекций в Excel); редирект входа принимает только
  относительные пути (open redirect закрыт).
- **Секреты:** в репозитории лежит только публичный anon-ключ (так и должно
  быть); `service_role` не копируется никуда; при его утечке — немедленная
  ротация в Supabase → Settings → API Keys.

- **Предпросмотр товара — изолированный iframe (v0.17.0, внешний ревью
  06.10.2026, находка A1):** модалка «Полный предпросмотр» в админке —
  `<iframe sandbox="">` без скриптов: токены брендбука передаются в
  предпросмотр статическим инлайн-`<style>`, собранным из кэша токенов
  брендбука со строгой валидацией каждого значения (цвет — только
  `#RRGGBB`-формат, типографика — только число). Дополнительно
  `brandvars.js` валидирует значения из кэша localStorage ДО применения
  к странице — CSS-инъекция через подменённый кэш токенов исключена.
  Автотест check-repo v2.6 запрещает `<iframe>` без sandbox и инлайновые
  `on*`-обработчики.
- **Лимиты длины полей заказа (v0.17.0, находка C3):** `create_order` v8 —
  имя/адрес/комментарий не длиннее 1000 символов (защита бандлов и
  CSV-экспортов от мусора); решение владельца 06.10.2026.
- **Границы дат промокодов — в локальном времени магазина (v0.17.0,
  находка C1):** `check_promo` v2 трактует `valid_from`/`valid_until`
  в Europe/Moscow (регламент времени — техпаспорт §11).

## 3. Чего в защите нет — и это осознанно (границы черновика)

| Чего нет | Последствие |
|---|---|
| Аутентификации админки: вход по ссылке, без пароля | Любой, у кого есть адрес `admin.html`, видит список заказов с контактами и может менять статусы и отметки оплаты |
| Мок-авторизация v0.4.0: пароль `123456` написан в коде `login.html` и указан на странице | Войти может любой, кто открыл страницу входа; это осознанно для демонстрации окна входа и неприемлемо в боевой версии. **Уточнение (внешний ревью 06.10.2026, A3): `mockauth.js` — косметический UX-гейт, а не механизм безопасности** — флаг сессии живёт во вкладке браузера, серверной сессии нет, страницы админки не защищены вообще |
| `REVOKE EXECUTE` на security definer-функциях отсутствует — админ-RPC (`admin_set_status`, `admin_set_paid`, `admin_set_return_*`, `admin_resolve_quarantine` и др.) вызываемы ролью anon | **Явное решение (внешний ревью 06.10.2026, A2):** в черновике админка работает под anon (мок-авторизация) — REVOKE сломал бы админ-панель; граница осознанная и зафиксирована здесь и в `supabase/README.md` («Решения»). В боевой версии — REVOKE FROM PUBLIC + гранты по ролям сессии (M2, `docs/plan/migration-plan.md` §5.1 п. 18) |
| Анонимный CRUD каталога и справочников (draft-политики baseline 02; исторически скрипты 07–16) | Любой с ссылкой на админку может править товары, цены, бренды, способы доставки/оплаты (включая удаление неиспользуемых — исторически скрипт 16), промокоды, луки, брендбук, тексты сайта, клиентов и причины возврата (удаление причин — только деактивацией); данные воспроизводимы из бэкапов CSV и baseline-скриптов 01–05, 09. Деньги и остатки при этом защищает сервер (функции, а не политики). В боевой версии запись идёт только через авторизованный API |
| Пароли пользователей `admin_users` — SHA-256 без соли, **колонка `password_hash` читается анонимно** (draft-политика чтения) | Хеш слабого пароля без соли дешифруется радужной таблицей мгновенно (фикс F25); для макета с вымышленными пользователями допустимо; в боевой версии — bcrypt/argon2id, соль и никакого публичного чтения хешей |
| Ролей, сессий, 2FA, журнала входов и аудита | Действия в админке не персонализированы и не журналируются |
| Ограничения частоты для админ-действий | Изменение статусов можно слать запросами без троттлинга |
| Отслеживание заказа (`track_order`) публично и перебираемо | Код подтверждения — 4 цифры телефона или 4 символа почты, номера заказов последовательны, троттлинга нет: историю статусов чужого заказа теоретически можно enumeration-ом подобрать (фикс F25). Наружу отдаются только названия статусов и даты — без контактов и администраторов. Создание заявки на возврат (`create_return_request`, v0.16.0) использует тот же код — перебираемо; защита макета: заказ только в статусе «Отправлен»/«Доставлен», одна незакрытая заявка на заказ, ≤3 заявок/10 минут на заказ. В боевой версии — rate-limit в middleware |
| Российского сервера для базы | Реальные ПДн хранить запрещено; только тестовые данные |
| Политики ПДн, согласия в формах, оферты | Опубликованы черновые шаблоны privacy.html и offer.html с плейсхолдерами [указать: …] и плашкой о тестовых данных; чекбоксы согласий в формах и финальные формулировки — в боевой версии |
| Защитных HTTP-заголовков (CSP, HSTS, X-Frame-Options) | GitHub Pages даёт HTTPS, но заголовки не настроены — запланировано в боевой версии |
| Бэкапов сверх автоматических бэкапов Supabase | Данные черновика воспроизводимы baseline-скриптами 01–05, 09 и бэкапами CSV |

Этот перечень продублирован баннером на самой `admin.html` и плашкой
на форме заказа. Перевод макета в боевой режим без устранения таблицы выше
**не допускается**.

## 4. Если что-то пошло не так (регламент черновика)

1. Утечка или компрометация ключей: ротация ключей в Supabase, проверка
   журнала запросов Database → Logs за период утечки.
2. Порча данных: новый стенд восстанавливается baseline-скриптами
   01→05, 09 → 26→27 и/или импортом бэкапов CSV (данные черновика не
   уникальны). **Живую базу baseline-скриптами не пересоздавать** — посевы
   перезапишут правки владельца (модель F21 — вариант 2+3 от 05.10.2026,
   с волны v0.17.0 в терминах «baseline заморожен + инкременты»: живая база
   получает только инкрементные скрипты ≥ 26). Исторические одноразовые
   data-миграции 06–08 и 25 исчезли как класс при консолидации (эффект зашит
   в посевы baseline; оригиналы — архив `supabase/archive/sql-01-25-v0160.md`);
   инкремент 27 — одноразовая миграция с guard по старому значению
   (повторный прогон — no-op).
3. Появление в базе реальных ПДн (кто-то оформил «настоящий» заказ):
   строки удаляются вручную из Table Editor, инцидент фиксируется
   в переписке участников проекта.

Для боевой версии регламент расширяется до отраслевого: уведомление
Роскомнадзора об утечке в 24/72 часа, резервные копии с проверкой
восстановления, аудит-журнал действий администраторов.
