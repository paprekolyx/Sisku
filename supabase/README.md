# supabase/ — скрипты изменения базы данных (черновик Sisku)

SQL-скрипты проекта Supabase `sisku-draft`. Выполняются в Supabase → SQL Editor.

**Модель с волны v0.17.0 (07.10.2026): консолидированный baseline + инкременты.**
- **Baseline `01–05, 09`** — состояние базы на v0.16.0-draft шестью скриптами
  (результат консолидации исторических скриптов 01–25; задание аналитика
  07.10.2026: минимальное количество скриптов для подъёма базы). Baseline
  **заморожен**: любые изменения схемы/логики/посевов — только новыми
  инкрементными скриптами с номера **26**.
- **Инкременты `26, 27, 28, 29, 30, …`** — правки следующих волн; применяются и к живой
  базе, и к новому стенду (в порядке номеров).
- **Новый стенд:** выполнить по порядку **01 → 02 → 03 → 04 → 05 → 09 → 26 → 27 → 28 → 29 → 30**
  (и далее каждый новый инкремент; последний — `30_client_segments.sql`). Все скрипты идемпотентны.
- **⚠ Живая база** (контент отредактирован владельцем): baseline НЕ
  перезапускать — посевы и миграционные части затрут правки (модель F21:
  «data-правки применяются один раз»). Живая база получает **только
  инкременты ≥ 26**. Скрипт 27 — одноразовая data-миграция с guard по старому
  значению (повторный прогон безопасен — no-op, но по регламенту один раз).
  Скрипт 28 — backfill истории существующих клиентов с тем же guard
  (повторный прогон — no-op). Скрипт 30 — посев только отсутствующих
  ключей `segments.*` (on conflict do nothing; повторный прогон — no-op).
- **История:** исторические скрипты 01–25 в дореволюционном виде (включая
  промежуточные версии функций create_order v1–v7, admin_set_status v1–v4 и
  одноразовые data-миграции 06–08, 25) — замороженный архив
  **`supabase/archive/sql-01-25-v0160.md`** (GitHub-репозиторий загружен
  07.10.2026 одним коммитом f19633a — история до v0.17.0 не сохранена, архив —
  единственный источник скриптов 01–25). Номера 06–08 и
  10–25 **не переиспользуются** (правило 3 регламента).

## Консолидация волны v0.17.0 (что и как проверено)

- Состав baseline собран программно из конечного состояния эталонной базы
  (прогон исторической цепочки 01→25 на свежем PostgreSQL 15.19): функции —
  `pg_get_functiondef` конечных версий, политики — из `pg_policies` (62 шт.),
  посевы — финальные значения таблиц, схема — из исходных скриптов (стиль и
  идемпотентные паттерны сохранены).
- **Верификация:** две свежие базы PostgreSQL 15 — (A) историческая цепочка
  01→25 + 26 + 27, (B) baseline 01→09 + 26 + 27 (двойной прогон —
  идемпотентность): нулевой дифф по колонкам, констрейнтам, политикам,
  индексам, определениям 18 функций, RLS-флагам, комментариям (49),
  последовательностям и данным 12 посевных таблиц; смоук-цепочка «заказ →
  статусы → заявка на возврат → карантин → осмотр → продажа», регресс отмены,
  лимиты 1000 (отказ и граница), промокод в московскую дату, бандлы, RLS под
  ролью anon — зелёные (60 проверок).
- Повторная консолидация baseline — регламентная процедура на вехах
  (кандидат: перед заморозкой черновика / стартом M0): пересборка из живого
  состояния + та же верификация двумя базами.

## Решения, зафиксированные в скриптах (чтобы не «потерять» при переносе в бой)

*(Номера скриптов в описаниях решений — исторические: структура и логика теперь
в baseline 01–05/09, оригиналы — в архиве `archive/sql-01-25-v0160.md`.)*

- **Удаление товаров запрещено by design** (ист. скрипт 11, ревью F49): DELETE-политики
  для `products` нет сознательно — товар архивируется через `is_active = false`,
  FK от `order_items` не даёт удалить товар с историей заказов. В боевой версии —
  soft-delete (`is_active`/`deleted_at`), физическое удаление не появляется.
- **Категории, бренды, варианты, луки, шаблоны брендбука** — DELETE-политики есть,
  защиту от удаления связанных данных обеспечивают FK (штатная ошибка 23503).
- **Способы оплаты/доставки** — DELETE-политики добавлены ист. скриптом 16 (ревью F09):
  способ без заказов удаляется, использованный в заказах защищён FK. Полное
  чтение справочников для anon (`using (true)`) — в baseline 02 (фикс V4:
  истина объекта в одном месте, повторный прогон не откатывает расширение).
- **F21 — решение (05.10.2026): вариант 2+3**, с волны v0.17.0 — в модели
  «baseline + инкременты»: исторические одноразовые data-миграции 06–08 и 25
  исчезли как класс (эффект зашит в посевы baseline, который на живой базе не
  перезапускается); одноразовые инкременты (сейчас 27) — с guard по старому
  значению и пометкой в шапке; в боевой версии факт применения каждой миграции
  фиксируется в `schema_migrations`, data-миграции — ровно один раз
  (`docs/plan/migration-plan.md`, чек-лист M1 п. 14).
- **Признак оплаты отделён от статусной модели окончательно** (ист. скрипт 18,
  волна v0.15.0, правка 2.2): отменённый заказ больше не блокирует `is_paid` —
  деньги могли поступить после отмены или быть возвращены; заблокированы
  только статусные переходы (`admin_set_status`). Событие смены оплаты пишется
  в `order_status_history` с автором (`p_changed_by`).
- **Имя клиента защищено флагом подтверждения** (ист. скрипт 19, `create_order` v7):
  `clients.name_confirmed` ставится при сохранении карточки клиента в админке —
  подтверждённое имя не перезаписывается новыми заказами (полная политика —
  П8а «история имён и слияния», v1.x).
- **Комплект сохраняется атомарно** (ист. скрипт 17): RPC `draft_save_look` —
  комплект и состав в одной транзакции; в бою — транзакция PDO (migration-plan M1).
- **Ключ `contacts.repo_url` оставлен намеренно** (решение аналитика 05.10.2026):
  ссылка на репозиторий убрана с витрины, но ключ в `site_content` сохраняется —
  может быть полезен в будущем. Из самопроверок и админки не убирается.
- **Карантин вместо авто-возврата в продажу** (ист. скрипт 23, волна v0.16.0,
  фикс F51; схема (а) счётчик — утверждена аналитиком 06.10.2026): при переходе
  заказа в «Возврат» единицы уходят в `quarantine_qty` («требует осмотра») и не
  продаются, пока осмотр (`admin_resolve_quarantine`) не вернёт их в `stock` или
  не спишет. Журнал складских движений — fp №3b (волна-кандидат после сдвига
  плана v0.17.0 — v0.29.0); в бою — боевая инвентаризация (migration-plan §5.1 п. 15).
- **Заявки на возврат пишутся только через RPC** (ист. скрипт 22): у
  `return_requests` нет политик записи — создание покупателем
  (`create_return_request`: серверная валидация заказа, кода подтверждения,
  статуса shipped/delivered, активной причины; антиспам — одна незакрытая
  заявка на заказ, 3/10 мин), обработка — `admin_set_return_status` /
  `admin_set_return_refund`. Причины возврата: DELETE-политики нет — удаление
  только деактивацией. `created_by`/`handled_by` — текст (паттерн
  `order_status_history.changed_by`): FK на пользователей — в боевой M2.
- **`used_count` промокода НЕ возвращается при отмене/возврате заказа**
  (внешний ревью 06.10.2026, находка C2 — решение владельца: задокументировать):
  лимит использований — маркетинговая защита, списание кода фактом создания
  заказа окончательное; возврат счётчика позволил бы накручивать лимит
  циклами «заказ → отмена». Статистика «Акций» трактует `used_count` как
  «сколько раз код применили к созданным заказам».
- **Регламент времени** (внешний ревью 06.10.2026, находка C1 — решение
  владельца 06.10.2026 «локальное время»): моменты времени — `timestamptz`
  (UTC в базе); календарные границы (даты действия промокодов) — в локальном
  времени магазина `Europe/Moscow` (`check_promo` v2, скрипт 26); относительные
  окна (анти-спам 3/10 мин) — интервалы, от часового пояса не зависят;
  фронтенд — локальная дата устройства (`dayKey()`, грабля №1). В боевом
  MySQL 8 — `CONVERT_TZ` (migration-plan §5.1 п. 19).
- **Лимит длины текстовых полей заказа — 1000 символов** (`create_order` v8,
  скрипт 26; решение владельца 06.10.2026 по находке C3 внешнего ревью):
  имя/адрес/комментарий; защита бандлов и CSV-экспортов от мусора/DoS.
- **EXECUTE на админ-RPC открыт для anon сознательно** (внешний ревью 06.10.2026,
  находка A2 — явное решение): мок-авторизация черновика работает под anon —
  `REVOKE EXECUTE` сломал бы админ-панель; SECURITY.md §3 фиксирует границу;
  в боевой версии — REVOKE FROM PUBLIC + гранты по ролям сессии
  (migration-plan §5.1 п. 18, волна M2).

## Правила написания скриптов (регламент проекта)

1. **Идемпотентность:** `create table if not exists`, `add column if not exists`,
   `drop policy if exists` перед `create policy`, `on conflict … do nothing` в посевах.
2. **Никаких разрушающих действий** (`drop table`, `truncate`, `delete` без where)
   без пометки DANGER и резервной копии.
3. **Один скрипт — одна задача;** номер файла не переиспользуется (номера 06–08
   и 10–25 остались в истории — следующий 31).
4. **Доллар-квоты только парные:** `as $$ … $$;`. Одиночный `$` — синтаксическая
   ошибка 42601; проверяется автотестом `tests/check-repo.py`.
5. **Системный каталог политик RLS:** колонка называется **`pg_policies.policyname`**
   (без внутреннего подчёркивания!). Писать `policy_name` — ошибка 42703.
   Автотест `tests/check-repo.py` падает, если в `supabase/*.sql` встречается
   `policy_name`.
6. **Префлайт проекта:** скрипты, которые могут быть выполнены не в том проекте
   Supabase, начинаются с `do $$ … to_regclass(…) … $$`-проверки наличия таблиц
   черновика и падают с понятным текстом (в baseline — скрипт 02; исторически —
   07, 09–21). Автотест падает, если в скрипте с `create policy` нет `to_regclass`.
7. **Комментарий в шапке:** что делает, зачем, безопасно ли; в конце — самопроверка
   select-ом ожидаемых значений.
8. **Агрегаты не вкладываются:** `count/sum/min/max/jsonb_agg/string_agg` нельзя
   ставить аргументом другой агрегатной функции на одном уровне запроса —
   Postgres отклоняет ошибкой 42803 «aggregate function calls cannot be nested».
   Нужен массив/объект из агрегатов — сначала `group by` в подзапросе или CTE,
   затем `jsonb_agg` по его строкам (см. `draft_clients_bundle()` v2).
   Ошибка семантическая: pglast и check-repo её не ловят, только прогон на Postgres.
9. **Baseline заморожен (с волны v0.17.0):** правки схемы, логики и посевов —
   только новыми инкрементными скриптами (≥ 26); baseline 01–05, 09 не
   редактируется (пересборка — регламентная процедура на вехах с верификацией
   двумя свежими базами, см. «Консолидация»). Урок грабли №15: **pglast не
   проверяет тела `language sql`-функций** — прогон на живом PostgreSQL
   обязателен для каждого нового скрипта.
