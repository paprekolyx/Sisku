# supabase/ — скрипты изменения базы данных (черновик Sisku)

SQL-скрипты проекта Supabase `sisku-draft`. Выполняются в Supabase → SQL Editor
по порядку номеров, все идемпотентны (повторный запуск не ломает структуру).
**Исключение — скрипты 06–08: одноразовые миграции данных** (решение F21,
05.10.2026 — вариант 2+3): для подъёма нового стенда выполняются полным
порядком 01→16, но на живой базе, где контент уже отредактирован через
админку, **повторно не запускаются** — перезапишут правки (подробности —
в разделе «Решения» ниже и в шапках самих скриптов).

## Решения, зафиксированные в скриптах (чтобы не «потерять» при переносе в бой)

- **Удаление товаров запрещено by design** (скрипт 11, ревью F49): DELETE-политики
  для `products` нет сознательно — товар архивируется через `is_active = false`,
  FK от `order_items` не даёт удалить товар с историей заказов. В боевой версии —
  soft-delete (`is_active`/`deleted_at`), физическое удаление не появляется.
- **Категории, бренды, варианты, луки, шаблоны брендбука** — DELETE-политики есть,
  защиту от удаления связанных данных обеспечивают FK (штатная ошибка 23503).
- **Способы оплаты/доставки** — DELETE-политики добавлены скриптом 16 (ревью F09):
  способ без заказов удаляется, использованный в заказах защищён FK. Полное
  чтение справочников для anon (`using (true)`) с v0.14.1 создаёт скрипт 02 —
  истина в одном месте (ревью v0.14.0, V4: повторный прогон 02 после 16 больше
  не откатывает расширение); граница «в заказе только активные» — на сервере.
- **F21 — решение принято (05.10.2026): вариант 2+3** (ревью v0.13.1 §4.3):
  **(2)** скрипты 06–08 помечены как **одноразовые миграции данных** в шапках
  и в этом реестре — на живой базе с отредактированным через админку контентом
  повторно не запускать; новый стенд поднимается полным порядком 01→16;
  **(3)** в боевой версии (MySQL) факт применения каждой миграции фиксируется
  в таблице `schema_migrations`, data-миграции выполняются ровно один раз
  (`docs/plan/migration-plan.md` v1.2.1, чек-лист M1 п. 14). Вариант 1
  (guard-скрипт по старому значению) **отклонён** — резервирование номера 17
  под F21 **снято**; следующий новый скрипт — 17 (задачи волны v0.15.0).
  Пометки в шапках 06–08 — документированное исключение из правила
  «существующие скрипты не редактируются» (только комментарии, SQL не менялся).
- **Ключ `contacts.repo_url` оставлен намеренно** (решение аналитика
  05.10.2026): ссылка на репозиторий убрана с витрины, но ключ в
  `site_content` сохраняется — может быть полезен в будущем (черновой макет
  станет архивной работой аналитика). Из самопроверок и админки не убирается;
  «косметический хвост 1» сверки чата закрыт без правок.

## Правила написания скриптов (регламент проекта)

1. **Идемпотентность:** `create table if not exists`, `add column if not exists`,
   `drop policy if exists` перед `create policy`, `on conflict … do nothing` в посевах.
2. **Никаких разрушающих действий** (`drop table`, `truncate`, `delete` без where)
   без пометки DANGER и резервной копии.
3. **Один скрипт — одна задача;** номер файла не переиспользуется.
4. **Доллар-квоты только парные:** `as $$ … $$;`. Одиночный `$` — синтаксическая
   ошибка 42601; проверяется автотестом `tests/check-repo.py`.
5. **Системный каталог политик RLS:** колонка называется **`pg_policies.policyname`**
   (без внутреннего подчёркивания!). Писать `policy_name` — ошибка 42703.
   Автотест `tests/check-repo.py` падает, если в `supabase/*.sql` встречается
   `policy_name`.
6. **Префлайт проекта:** скрипты, которые могут быть выполнены не в том проекте
   Supabase, начинаются с `do $ … to_regclass(...) … $`-проверки наличия таблиц
   черновика и падают с понятным текстом. С v0.14.0 (ревью F20) префлайт
   обязателен во **всех** скриптах, создающих политики или draft-объекты
   (02, 07, 09–16); автотест `tests/check-repo.py` падает, если в скрипте
   с `create policy` нет `to_regclass`.
7. **Комментарий в шапке:** что делает, зачем, безопасно ли; в конце — самопроверка
   select-ом ожидаемых значений.
8. **Агрегаты не вкладываются:** `count/sum/min/max/jsonb_agg/string_agg` нельзя
   ставить аргументом другой агрегатной функции на одном уровне запроса —
   Postgres отклоняет ошибкой 42803 «aggregate function calls cannot be nested».
   Нужен массив/объект из агрегатов — сначала `group by` в подзапросе или CE,
   затем `jsonb_agg` по его строкам (см. `draft_clients_bundle()` v2 в скрипте 15).
   Ошибка семантическая: pglast и check-repo её не ловят, только прогон на Postgres.
