# supabase/ — скрипты изменения базы данных (черновик Sisku)

SQL-скрипты проекта Supabase `sisku-draft`. Выполняются в Supabase → SQL Editor.

**Модель (ревизия 2 — волна v0.21.1, 17.10.2026): консолидированный baseline + инкременты.**
- **Baseline `01–05, 09` (ревизия 2)** — состояние базы на **v0.21.0-draft**
  шестью скриптами: 30 таблиц, 72 политики, 29 функций (20 ядра + 9 бандлов),
  73 ключа `site_content`, посев каталога (8 демо-товаров, 20 вариантов,
  бейдж «New» всем товарам). Первая ревизия baseline (v0.17.0) фиксировала
  состояние на v0.16.0; ревизия 2 поглотила инкременты **26–33** (волны
  v0.17.0–v0.21.0) — они заморожены в архиве `archive/sql-26-33-v0210.md`.
  Baseline **заморожен** (правило 9): любые изменения схемы/логики/посевов —
  только новыми инкрементными скриптами с номера **34**.
- **Инкременты `34, 35, …`** — правки следующих волн; применяются и к живой
  базе, и к новому стенду (в порядке номеров).
- **Новый стенд:** выполнить по порядку **01 → 02 → 03 → 04 → 05 → 09**
  (и далее каждый новый инкремент ≥ 34). Все скрипты идемпотентны
  (двойной прогон baseline верифицирован — самопроверки идентичны).
- **⚠ Живая база** (контент отредактирован владельцем): baseline НЕ
  перезапускать — посевы и миграционные части затрут правки (модель F21:
  «data-правки применяются один раз»). Живая база уже находится в состоянии
  v0.21.0 (инкременты 26–33 применены 07–17.10.2026) и получает **только
  инкременты ≥ 34**.
- **История:** исторические скрипты 01–25 — замороженный архив
  **`archive/sql-01-25-v0160.md`** (единственный источник; GitHub-репозиторий
  загружен 07.10.2026 одним коммитом f19633a — история до v0.17.0 не
  сохранена); инкременты 26–33 — замороженный архив
  **`archive/sql-26-33-v0210.md`** (единственный источник их содержимого
  в рабочей области после консолидации; к живой базе повторно НЕ
  применяются — эффект уже внесён). Номера **06–08, 10–25, 26–33 не
  переиспользуются** (правило 3 регламента). Baseline ревизии 1 (состояние
  на v0.16.0, 07.10.2026) доступен в git-истории GitHub (коммиты волн
  v0.17.0–v0.21.0).

## Регламент написания скриптов (действующий)

1. Новый скрипт — инкрементный, с очередного номера (следующий — **34**);
   номера 06–08, 10–25, 26–33 не переиспользуются.
2. Шапка: цель, версия волны, идемпотентность, порядок применения; в конце —
   самопроверка select'ом точных ожидаемых значений (строка приводится
   дословно в файле и в инструкции волны).
3. Идемпотентность: `create table if not exists` / `add column if not exists` /
   DO-guard констрейнты / `drop-create policy` / `on conflict do nothing` /
   `create or replace function`; одноразовые data-операции — с guard по
   старому значению (повторный прогон — no-op).
4. Системный каталог политик — `pg_policies.policyname`; доллар-квоты только
   парные `$$`; **регэкспы без якоря-доллара** (урок v0.19.0 + волна v0.21.0:
   проверка «только цифры» — паттерном `[^0-9]`); файлы с `$` править только
   программно (грабля `$`-коллапса).
5. Самопроверка числа функций — **по явному списку проектных имён** (методика
   Д11, волна v0.21.0): на живой базе зафиксирован платформенный объект —
   `rls_auto_enable` (event-trigger-функция авто-включения RLS из официальной
   документации Supabase; диагностика 17.10.2026 — список аналитика, 30 имён
   = 29 проектных + rls_auto_enable); судьба (оставить/удалить) — решение
   аналитика, трекер АН-30; голое общее число — справочным запросом,
   не сравнивается.
6. Прогон на живом PostgreSQL 15 обязателен для каждого нового скрипта
   (грабля №15: pglast не проверяет тела `language sql`-функций); чтение
   страницы — одним бандлом (грабля №6); блокировки — FOR UPDATE в
   детерминированном порядке (F23).
7. Пересборка baseline — регламентная процедура на вехах (решение аналитика):
   генератор из каталога эталона + верификация «две свежие базы + нулевой
   дифф + смоук + RLS + идемпотентность» (инструменты — `workaichat/pgtest/`).
