##### 4.3. Раскрытие вопроса 9 (по просьбе аналитика): повторный прогон миграций 06–08 на живой базе

**В чём дело.** Скрипты проекта делятся на два класса: (а) *создающие* (таблицы, политики, функции, посевы) — они идемпотентны и безопасны при любом числе прогонов; (б) *миграции-правки данных* — 06 (тексты контактов: «Написать в Telegram», `contacts.repo_url`), 07 (текст `order.payment.text`), 08 (описание платка 30001). Класс (б) выполнен как безусловные `UPDATE site_content SET value='…' WHERE key='…'` / `UPDATE products SET description='…' WHERE article='30001'`.

**Сценарий проблемы.** База поднята, владелец/аналитик через админку («Управление → Сайт») отредактировал текст `order.payment.text` под реальные условия. Позже кто-то восстанавливает демо-стенд или «на всякий случай» прогоняет все скрипты 01–15 подряд (регламент именно так и предписывает поднимать базу заново; check-repo и самопроверки поощряют повторный прогон). Скрипт 07 **молча затирает** отредактированный текст дефолтным. Формально идемпотентность не нарушена (второй прогон даёт тот же результат, что первый), но нарушено неочевидное ожидание: «повторный прогон безопасен для живой отредактированной базы». Для текстов это малозаметно, но тот же паттерн в бою (правки боевого контента + повторный прогон миграций) затрёт уже настоящие данные.

**Почему это не блокер.** В черновике тексты — заглушки, правки воспроизводимы; сценарий требует ручного повторного прогона старых миграций на наполненной базе — редкое событие.

**Варианты решения (для выбора):**
1. **Guard по старому значению** (рекомендую): `update site_content set value='…' where key='order.payment.text' and value='<прежний дефолт>'` — правка применяется, только если текст не редактировали. Плюс: полная автоматическая безопасность повторного прогона. Минус: скрипты 06–08 придётся выпустить как новую ревизию (по регламенту — новым скриптом 16+ или правкой с пометкой), а прежние значения нужно точно знать.

3. **Ничего не делать** в черновике, а правило «миграции данных не перезаписывают отредактированные значения» закрепить в регламенте боевой версии (для MySQL-миграций это стандартная практика: data-migration выполняется один раз, факт применения фиксируется в таблице `schema_migrations`). Плюс: честно — проблема боевая, не черновая. Минус: в черновике сценарий остаётся теоретически возможным.

##### 5.1. Чек-лист M1 (внесён ревизией v1.1 по ревью: F16, F22, F25, F48, F49, F05/F06; п. 10–11 — ревизия v1.1.1 по ревью v0.14.0: N3, N4)

Транзакционная дисциплина (plpgsql-функция атомарна по построению, PHP — нет):
1. В каждом сервисе — явные `beginTransaction/commit/rollback` **на всех путях** (включая catch); `SELECT … FOR UPDATE` вручную: строка заказа (смена статуса), строки товаров/вариантов в детерминированном порядке (товары по id, затем варианты по id), строка промокода, строка клиента при UPSERT.
2. MySQL-диалект: `key`/`comment`/`value` (site_content, brand_colors, deliveries) — зарезервированные слова: переименовать колонки при порте или всегда backticks; `jsonb` → JSON MySQL 8 или плоские параметры контракта; CHECK-констрейнты MySQL 8 работают (total >= 0 перенести).
3. Индексы: InnoDB создаст FK-индексы сам; статистические добавить вручную: `orders(status_id, created_at)`, `orders(client_id)`, `order_items(order_id)`/`(variant_id)`, `order_status_history(order_id)`, `deliveries(order_id)`, `look_items(look_id)`.
4. `orders.total` — уточнить комментарий колонки (net: за вычетом promo_discount/look_discount); для бухгалтерии/маржи решить — `gross_total` колонкой или вычисление из снапшотов `order_items` (feature-proposals №8/№11).
5. `deliveries` — решить судьбу: слить в `orders` или оставить под трек-номер/мультидоставку (в черновике дублирует address/cost).
6. `POST /api/orders` — идемпотентность-ключ (защита двойной отправки), rate-limit на `POST /api/track`.
7. Продукты — только soft-delete (`is_active`/`deleted_at`): DELETE запрещён by design ещё в черновике (F49).
8. XSS/CSV на сервере: whitelist схем для href-полей (аналог `safeUrl`), анти-формульный префикс в серверных CSV-экспортах (аналог `csvCell`), экранирование вывода.
9. Согласия ПДн: поле `consent` в `POST /api/orders` → запись в `consents` (F48); `policy_version` в `GET /api/content`.
10. Промокоды: под блокировкой `SELECT … FOR UPDATE` перепроверять **одним условием весь набор** — `is_active` + сроки (`valid_from`/`valid_until`) + минимальная сумма + `usage_limit`, а не только лимит (в черновике `check_promo()` валидирует сроки/минимум без блокировки строки — окно в миллисекунды; в PHP без атомарности plpgsql это критичнее; ревью v0.14.0, N3).
11. Клиенты: серверная валидация **формата** контакта до создания клиента — заказ с телефоном без цифр и без e-mail отклонять читаемой ошибкой, а не создавать клиента без ключей дедупликации (`phone_key`/`email_key` = null плодит дубликаты при каждом следующем таком заказе; в черновике недостижимо через витрину, но достижимо прямым RPC-вызовом; ревью v0.14.0, N4).
12. Порт схемы — сразу с резервом под принятые в план пункты (дешевле заложить колонки при порте, чем мигрировать боевую базу): `product_variants.price_override` (записка 3 — цены вариантов), `looks.partial_policy` (записка 11), `deleted_at` у удаляемых сущностей (записка 31 — soft-delete), `clients.name_confirmed` + история имён (записка 8а), `notification_templates` (§4.4, ответ 2.7), `orders.gross_total` — по решению F52 (feature-proposals №8/№11).
13. Уведомления: e-mail-канал владельцу — с первого дня M1 (сквозной сценарий приёмки зависит от него); шаблоны — из `notification_templates`, никаких захардкоженных текстов (ответ 2.7); исследование бесплатной интеграции ВКонтакте — **очень низкий приоритет, не актуально до запуска боевого проекта** (решение 05.10.2026, обновляет ответ 3.8).
14. Дисциплина data-миграций (**решение F21 — вариант 2+3, 05.10.2026**): в `db/` ведётся таблица `schema_migrations` — факт применения каждой миграции фиксируется, data-миграции выполняются **ровно один раз**; правки данных не должны перезаписывать значения, отредактированные через админку (в черновике — скрипты 06–08 помечены «одноразовые» в шапках и в `supabase/README.md`; повторный прогон на живой отредактированной базе запрещён регламентом).

##### 4.7. Эксплуатация

## 6. Правила ведения трекера

1. **Обновление:** при закрытии пункта (статус, дата, куда внесено решение), при получении новых ответов/решений, при старте каждой волны (v0.15.0, M0…). Версия документа повышается, в шапке добавляется строка ревизии.
2. **Синхронизация:** закрытие пункта здесь сопровождается закрытием в первоисточнике (заметки §3, опросник, обработка §3, реестр §8) — и наоборот. При расхождении приоритет у первоисточника.
3. **Дословность:** копии блоков не редактируются (уровень заголовков сдвинут на +2 — единственное изменение); при изменении редакции источника копия обновляется вместе с указанием новых строк.
4. **Публикация:** документ рабочий, на GitHub не публикуется; зарегистрирован в реестре документации §5.5.
5. **Расположение записей ревизий (с 06.10.2026, записка Д1 приёмки v0.15.0):** записи версий/ревизий — в нижней части документа (раздел «История ревизий»); после поля «Статус» идёт поле «Назначение». Применено к трекеру (ред. 1.7), migration-plan (v1.4), ТЗ (v1.4), опроснику (ред. 1.4), заметкам (2.1), реестру документации (2.0); новые документы создаются сразу по этому правилу; исторические/замороженные не перестраиваются.
6. **Период ручного ведения (с 06.10.2026):** якоря билдера `build-ozhidaemye-deystviya.py` сломаны новыми редакциями источников — в fp редакции 2 удалён раздел «Как приоритизировать» (копия §4.3), в опроснике ред. 1.3 удалена секция «Мини-формат» (копия §2.1), migration-plan/ТЗ/техпаспорт — ревизии 1.3. До пересборки скрипта трекер ведётся ручной правкой (шапка, §0, статусные строки); дословные копии соответствуют редакциям источников до оборота АН-17 и помечены историческими в §2.1/§2.2. Список пересборки — реестр §5.5. **Расположение с 05.10.2026 — корень рабочей области (`~/ozhidaemye-deystviya.md`, перенесён из `new-shop-plan/` для быстрого доступа).** Если понадобится передать владельцу отдельный документ (матрица ролей — уже `docs/plan/matrica-dostupa.md`, feature-proposals, ТЗ) — он оформляется отдельно (АН-04.3/СВ-07).
