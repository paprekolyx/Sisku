## 2. Находки

### Находка 1 (🟡, требуется диагностика на живой базе). `func_count_28` = 29 вместо 28

**Суть проверки:** самопроверка скрипта 32 считает **все** функции схемы
`public` (`pg_proc`), эталон — 28 на свежем PostgreSQL 15.19 (верификация
волны v0.20.0). Проектный набор 28 функций = 18 (baseline 03/09) + 2
(скрипт 29: `admin_update_client`, `draft_client_card_bundle`) + 8 (скрипт
32) — полный список с сигнатурами: приложение А.

**Анализ:**
- Все 28 проектных функций на живой базе **присутствуют и работают**
  (9 × `t` в самопроверке 32; REST-сверка §1.3 исполняла бандлы и RPC).
  Расхождение — **ровно одна лишняя функция**, не входящая в проектный набор.
- Лишняя функция **не могла прийти из цепочки скриптов**: архив 01–25
  создаёт ровно те же 18 имён, что и baseline (единственный `DROP FUNCTION`
  в архиве — старая сигнатура `admin_set_paid(integer, boolean)` — учтён);
  консолидация v0.17.0 верифицирована нулевым диффом двух свежих баз
  (цепочка 01→25+26+27 против baseline+26+27 — 18 функций с обеих сторон);
  инкременты 26–32 создают только проектные функции (26/29/30/32 —
  create or replace; 27/28/31 — DO-блоки и схема, функций не создают).
  На свежей базе вся цепочка 01→32 даёт ровно 28.
- Следовательно, 29-я функция — **дрейф живой базы**: наиболее вероятные
  источники — (а) функция, созданная вручную в SQL Editor (отладка/разовая
  операция в период 01–10.10); (б) платформенный объект Supabase в схеме
  `public`; (в) дрейф существовал и раньше: самопроверка скрипта 29 выводила
  голое число (`…|20`) — если на живой базе тогда было 21, это могло остаться
  незамеченным (в отчётах v0.18.0/v0.19.0 сверка живой базы — только REST,
  подсчёт функций не фиксировался).
- **Удалённо имя не определяется:** OpenAPI-спецификация PostgREST
  (`GET /rest/v1/`) требует secret-ключ (проверено — HTTP 401 «Secret API
  key required»); подсказки «Possible alternatives» в PGRST202 эта версия
  PostgREST не выдаёт (проверено зондом); pg_proc через REST не читается.

**Действие (аналитик, SQL Editor):** выполнить диагностический запрос
(приложение Б) и прислать список. Дальше — по итогу:
- если это **сирота ручной отладки** — удалить (`DROP FUNCTION IF EXISTS
  public.<имя>(<аргументы>);`) и зафиксировать запись в отчёте следующей
  волны; влияние на функциональность — нулевое;
- если это **платформенный объект Supabase** — не удалять; зафиксировать
  как допустимый дрейф живой базы и **изменить методику самопроверок**:
  со скрипта 33 считать не «голое количество функций в public», а сверять
  количество **по явному списку проектных функций** (или `count(*) … where
  proname = any (array[…28+новых…])`) — чтобы платформенные/ручные объекты
  не давали ложных расхождений (кандидат в урок для регламента — грабля №19,
  решение — за аналитиком);
- в любом случае: **волна v0.20.0 функционально применена полностью** —
  расхождение информационное, работу не блокирует, данные не затронуты.

## Приложение Б. Диагностический запрос (SQL Editor, живая база)

```sql
-- Все функции схемы public живой базы (ожидаем 29 строк; эталон — 28, приложение А)
select p.proname || '(' || pg_get_function_identity_arguments(p.oid) || ')' as sig,
       coalesce(left(obj_description(p.oid, 'pg_proc'), 60), '—') as comment
from pg_proc p
join pg_namespace n on n.oid = p.pronamespace
where n.nspname = 'public'
order by 1;
```

Лишняя строка (её нет в приложении А) — и есть 29-я функция. Если
`pg_get_function_identity_arguments` недоступен — заменить на
`pg_get_function_arguments(p.oid)`. Запрос только читает каталог — данных
не меняет.
