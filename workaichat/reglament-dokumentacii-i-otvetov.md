# Регламент ведения документации и подготовки ответов ИИ · Проект Sisku

**Редакция 2.0 · 17.10.2026 · Статус:** рабочий регламент в корне
`workaichat/` (вместе с трекером `ozhidaemye-deystviya.md`). Назначение —
закрепить накопленные правила ведения документов и подготовки пакетов волн,
а также формат ответов ИИ-ассистента (разработчика волн) в чате. Регламент
не заменяет источники (viki-reestr, инструкции update-vXXX, трекер) — при
расхождении приоритет у источника, регламент подлежит правке.

**Основание и источники.** Правила собраны из действующих документов проекта:
`docs/viki-reestr.md` (циклы обновления, фиксированный состав разделов
update-инструкции §2.2), трекер §1.13 (регламент публикации), инструкции
`docs/update/update-v0141…v0211.md` (эталон формата; §7 — уроки), реестр
граблей (№1–№18 — viki-reestr §2.12/§4.3, уроки update-vXXX §7), решения
F21/F23/F32. **Редакция 2.0 — по заданию аналитика 17.10.2026 (пункты 3–4):**
жизненный цикл черновиков, один объединённый отчёт на оборот, SECURITY/
LICENSE без версионных шапок, setup-supabase без изменчивых данных,
единственный источник реестра скриптов — supabase/README.md. Регламент из
ДРУГОГО проекта так и не поступил — его идеи вносятся отдельной правкой по
предоставлении файла.

## 1. Роли и каналы оборота

| Роль | Кто | Что делает |
|---|---|---|
| Владелец | владелец магазина | решения, ответы на вопросы опросника, контент, приёмка |
| Аналитик | ведущий аналитик (Albert23NO@ya.ru) | задания волн, решения Д#, загрузка пакетов на GitHub, применение SQL на живой базе, документооборот, приёмка с владельцем |
| Разработчик | ИИ-ассистент | исполнение волн: черновик → код/SQL → тесты → документы → отчёт; сверки загрузки |
| Внешний ревьюер | периодически | независимое ревью (отдельный документ на раунд — `docs/review/`) |
| Юрист | с M4 | юридические позиции (гейт M4/первого заказа) |

Каналы: чат (задания аналитика ↔ ответы разработчика), GitHub-репозиторий
(пакеты волн — загружает аналитик через Web UI), GitHub-wiki (записки
аналитика — страница для аналитика, разработчиком не синхронизируется —
решение 06.10.2026), живая база Supabase (скрипты применяет аналитик
в SQL Editor; разработчик сверяет результат через REST).

## 3. Порядок подготовки и исполнения волны

1. **Задание аналитика** — «начинаем волну vX.Y.Z» (цитируется дословно
   в «Основании» отчёта).
2. **Черновик инструкции** — разработчик готовит `work/draft/update-vXXX-chernovik.md`
   (**вне клона**; решение аналитика 09.10.2026 — «сначала черновик»):
   состав волны, открытые вопросы с рекомендациями разработчика (нумерация
   Д#), план смоука, предварительное дерево §2. **Жизненный цикл черновика
   (решение аналитика 17.10.2026):** черновик создаётся всегда по одному пути
   `work/draft/update-vXXX-chernovik.md`; после обработки (исполнения волны
   или снятия задания) черновик **удаляется из рабочей области чата** —
   состав волны фиксируют инструкция update-vXXX и отчёт; черновики не
   накапливаются и в репозиторий не попадают.
3. **Решения аналитика** — Д1…Дn. Пункты, не вошедшие в ответ, исполняются
   **по рекомендациям разработчика** и помечаются в отчёте (§3 — как Д13–Д15
   волны v0.20.0). Переопределения до старта — принимаются; после старта —
   только следующей волной/патчем.
4. **Исполнение:**
   * SQL — новый инкрементный скрипт с очередного номера (сейчас следующий —
     **34**; номера 06–08, 10–25, 26–33 не переиспользуются): шапка (цель,
     версия волны, идемпотентность, порядок) + префлайт + самопроверка
     select'ом **точных ожидаемых значений** (строка приводится в скрипте и
     в инструкции §4 дословно; число функций — **по явному списку проектных
     имён**, методика Д11 — голое общее число справочным запросом: на живой
     базе допустим платформенный дрейф); идемпотентность — create if not
     exists / create or replace / on conflict do nothing / drop … if exists;
     разовые data-операции — с guard по старому значению (повторный прогон —
     no-op); **живая база получает только инкременты ≥ 34** (модель F21 —
     baseline не перезапускать); многошаговые записи — одной транзакцией;
     блокировки — FOR UPDATE в детерминированном порядке (F23); пересборка
     baseline — регламентная процедура на вехах по решению аналитика
     (генератор из каталога эталона + верификация «две свежие базы + нулевой
     дифф + смоук + RLS + идемпотентность»; эталон v0.17.0/v0.21.1 —
     `workaichat/pgtest/build_*.py`, `verify_*.py`);
   * фронтенд — vanilla JS без сборки; **чтение страницы — одним бандлом**
     (SECURITY DEFINER RPC, грабля №6 — без N+1); запись каталога/справочников
     в черновике — draft-CRUD напрямую (осознанная граница); утилиты — только
     `util.js` (экранирование, whitelist схем, маски, CSV-защита от формул —
     F32); изменяемые тексты — из `site_content`, без хардкода (правило п.11);
     `config.js` — ключи БД и SITE_VERSION, больше ничего;
   * документы — по §2 регламента; тексты без CJK-вкраплений, без смешения
     алфавитов в идентификаторах, `$` в SQL/MD правится только программно
     (нечёткие замены дают `$`-коллапс) + скан дублей заголовков.
5. **Верификация разработчика (до отчёта):**
   * прогон всей цепочки скриптов на **свежем PostgreSQL 15** (самопроверки
     всех скриптов — дословно; грабля №15: pglast не проверяет тела
     language-sql функций — прогон обязателен);
   * смоук волны (сценарии S1…Sn + регрессы + RLS под anon + повторный прогон
     инкремента — no-op); драйвер и сценарии — в `workaichat/pgtest/`;
   * `node --check` всех изменённых JS;
   * `python3 tests/check-repo.py` — **exit 0** (в рабочей копии и в
     симуляции пакета на свежем клоне);
   * сканы: CJK — 0; одиночные `$` в supabase/*.sql — 0; смешение алфавитов — 0;
     дубли заголовков MD — 0 (`grep -c '^# '` = 1); первые байты изменённых
     HTML — `<!DOCTYPE html>`.
6. **Отчёт оборота** (§6 регламента) → аналитику.
7. **Загрузка аналитиком:** скрипты на живой базе (по инструкции §4 п.1,
   самопроверки сверить до символа) → GitHub Web UI: пакет по §2 инструкции
   (порядок: **скрипты → новые файлы → перезапись → config.js точечно
   последним**) → Pages публикуется автоматически.
8. **Сверка разработчика** в следующем обороте: свежий клон (check-repo,
   состав, маркеры редакций, первые байты) + живой сайт (версия, побайтово
   ключевые файлы) + REST-сверка живой базы → **входит в объединённый отчёт
   следующего оборота** (§0; отдельный файл сверки больше не создаётся —
   решение 17.10.2026). Находки — нумерованные, с критичностью 🔴/🟡/⚪.
9. **Приёмка с владельцем** — чек-лист инструкции §4 п.4 + универсальный
   чек-лист приёмки (по запросу аналитика). Замечания приёмки → вики-записки
   → `docs/priemka/priemka-v0XX.md` → следующие волны.

## 4. Формат инструкции `docs/update/update-vXXX.md` (фиксированный состав — viki-reestr §2.2, образец v0141/v0200)

Шапка: заголовок «Инструкция по обновлению черновика до vX.Y.Z-draft (волна …)»;
«Куда смотреть» (что за волна); «Основание» (fp №, план развития §, требования
владельца дословно, решения Д# с датами); «Версия сайта» (SITE_VERSION +
предупреждение: в GitHub-копии config.js править **точечно, только эту строку** —
в файле настоящие ключи БД).

Разделы:
1. **Что изменилось (состав волны)** — 1.0 решения до старта (Д# — дословно/
   сводка); 1.1 база (скрипты: состав, самопроверочные строки, счётчики
   таблиц/политик/функций/скриптов, следующий номер, бэкапы data/); 1.2+ —
   админка/витрина по страницам и модулям; тесты; документы.
2. **Файлы для загрузки в репозиторий** — дерево **от корня клона, с
   углублением в папки** (грабля №18; эталон — update-v0170 §2); каждое
   дерево-элемент с пометкой: `(НОВЫЙ)` / `(перезапись; что меняет)` /
   `(⚠ ТОЧЕЧНО: только строка SITE_VERSION → '…'; ключи БД не трогать)` /
   `(УДАЛИТЬ на GitHub)`; постоянные напоминания: SITE_VERSION в GitHub-копии
   config.js; синхронизация docs/plan/*.md (правило v0.14.1); пути docs/ —
   только по структуре подпапок; итог — «Всего: N новых, M перезаписываемых,
   K удаляемых» + что НЕ затрагивается + оговорка «изменения `workaichat/` —
   вне этой инструкции (список — в сообщении разработчика)». Перед деревом —
   порядок: **скрипты на живой базе → новые файлы → перезапись → удаления →
   config.js точечно**.
3. **Версия (точки синхронизации)** — таблица: config.js, шапка README,
   строка таблицы версий README, техпаспорт, viki-reestr (редакция),
   счётчики БД, «следующий скрипт» в supabase/README, строка check-repo.
   (SECURITY/LICENSE — вне точек синхронизации с 17.10.2026: отметка
   «Версия: смотреть в README.md».)
4. **База, публикация и проверка** — п.1 скрипты на живой базе (номера,
   порядок, ожидаемые строки самопроверок дословно, оговорки F21/одноразовости;
   для PATCH-волн без SQL — явная запись «живая база не меняется»);
   п.2 Pages; п.3 отсылка к §2; п.4 контроль после загрузки (свежий клон —
   check-repo exit 0; первые байты HTML — грабля №17в; REST-сверка — конкретные
   ожидаемые значения; живой сайт — версия; ручные сценарии — нумерованные,
   каждый «глазами»); п.5 бэкапы data/ (что выгружает аналитик, что НЕ
   выгружается — чувствительное и операционное).
5. **Финальная проверка (выполнена разработчиком до загрузки)** — цепочка/
   смоук/RLS/no-op/node --check/check-repo/сканы — фактические результаты.
6. **Открытые пункты (не входят в волну)** — нумерованные, со сроками/адресатами.
7. **Урок для регламента** — если волна дала новую граблю (номер — следующий
   по реестру; фиксация — здесь + viki-reestr + этот регламент).
Приложения: **А** — смоук (таблица сценариев и результатов); **Б** — формы
RPC/схем фактические (для сверки и будущей приёмки).

## 5. Формат ответа ИИ (разработчика) в чате

1. **Состав ответа:** (а) что сделано — кратко, с ключевыми результатами
   верификации (цифры: смоук N/N, check-repo exit 0, счётчики); (б) **список
   изменённых файлов** — репозиторий (по папкам) и **отдельно `workaichat/`**
   (изменения workaichat перечисляются **только в теле текстового ответа**,
   в документах репозитория не упоминаются — указание аналитика 10.10.2026);
   (в) «ожидает от аналитика» — нумерованный список (скрипты, загрузка,
   удаления на GitHub, решения, подтверждения); (г) вопросы — если есть.
2. **Вопросы — до старта, одним сообщением** (консолидированно; не серией
   уточнений по ходу исполнения). Открытые пункты черновика — нумерацией Д#
   с рекомендациями разработчика.
3. **Без дублирования документов:** в чате — выжимка и указатели (файл §п.),
   не пересказ разделов. Цитаты заданий/решений аналитика — дословно
   (в отчёте — блок «Основание»).
4. **Отчёты — только действия и изменения** (заметки аналитика §6 п.2,
   ред. 06.10.2026): описания ревизий в рабочих файлах не ведутся (история —
   в архивных копиях и viki-reestr); версия/редакция — в шапке.
5. **Оформление:** русский язык; даты — ДД.ММ.ГГГГ; номера версий — SemVer
   0.x (MINOR — волна, PATCH — гигиена, без функционала); идентификаторы
   пунктов — устойчивые (АН-/ВЛ-/ЮР-/СВ-/Д#/F##/грабля №N — не перенумеровываются,
   закрытые не переиспользуются); статусы — 🔴/🟡/⚪/✅ (семантика — трекер
   «Как читать»).
6. **Что не делается без явного указания аналитика:** публикация/коммиты
   на GitHub (загружает аналитик); правка замороженных [З] документов;
   обновление универсального чек-листа приёмки; архивация трекера; удаление
   файлов репозитория (кроме предусмотренного планом волны — удаления
   фиксируются в инструкции §2 пометкой «УДАЛИТЬ на GitHub»); изменения
   живой базы (разработчик — только чтение через REST; диагностические
   RPC-пробы — только идемпотентные, с фиксацией в отчёте).

## 6. Формат отчётов (`workaichat/reports/`) — ред. 2.0: ОДИН отчёт на оборот

**Решение аналитика 17.10.2026:** отдельные отчёты сверки и диагностики
больше не создаются — оборот разработчика сопровождается **одним**
объединённым отчётом; пересказ состава волны из опубликованной инструкции
`docs/update/update-vXXX.md` в отчёте **запрещён** (только ссылка на раздел
и цифры верификации). Прежние форматы `sverka-zagruzki-*.md` и
`diagnostika-*.md` — упразднены (исторические файлы удалены с GitHub
аналитиком 17.10.2026, объединённые редакции сохранены).

**Имена:** волновой оборот — `otchet-volna-vXXX-DD-MM-YYYY.md`; служебный
оборот (сверка/ревизия/диагностика без новой версии функционала) —
`otchet-oborot-<тема>-DD-MM-YYYY.md`.

**Состав объединённого отчёта** (разделы — по факту оборота; пустые не
создаются):
* шапка: Разработчик; Основание — дословная цитата задания; тип оборота
  (MINOR/PATCH/служебный); версия рабочей копии; статус пакета («ждёт
  загрузки» / «загружен, сверка в §0 следующего оборота»);
* §0 **Сверка и диагностика** (если обороту предшествовала загрузка или
  правки аналитика): клон/HEAD/инструменты; подтверждено (пакет, Pages,
  живая база — таблицей ожидание/факт); **находки** — нумерованные,
  критичность 🔴 требует правки / 🟡 нужна диагностика или решение /
  ⚪ информационная (суть, анализ, действие);
* §1 **Состав исполнения**: новые/изменённые файлы репозитория (списком,
  без описания содержимого — описание в update-vXXX §1–§2); документы
  оборота; workaichat — списком в тексте ответа (не в отчёте);
* §2 **Верификация** (цифры): цепочка скриптов и самопроверочные строки,
  смоук N/N, RLS, no-op, node --check, check-repo vX.Y — exit 0, сканы;
* §3 **Решения и отметки**: Д# исполненные/по рекомендациям; что не менялось
  и почему; открытое до приёмки/боевых вех;
* §4 **Ожидает от аналитика** (нумерованно: скрипты → загрузка → удаления →
  контроль → приёмка → следующая волна).
Приложения — только если нужны эталоны/диагностические запросы.

## 7. Гигиена файлов и данных

* **Черновики `work/draft/`** — вне клона; путь постоянный
  (`work/draft/update-vXXX-chernovik.md`); после исполнения — **удаляются**
  (решение 17.10.2026); в репозиторий не попадают.
* **Реестр скриптов** (состав, порядок, самопроверочные строки, следующий
  номер) — единственный источник `supabase/README.md`; другие документы —
  указатели (решение 17.10.2026).
* **Грабля №17в** (решение 10.10.2026): ведущие CRLF-строки, добавляемые
  GitHub Web UI загружаемым HTML/CSS, временно оставляем; проверка первых
  значимых байтов после каждой загрузки; **перед M1 — очистка** (пакет АН-29).
* **Бинарные файлы:** после загрузки — контроль размеров (грабля №17;
  фото — WebP; исходники JPG — служебные папки `.jpg/`, через Pages не
  публикуются).
* **data/:** выгружаются только справочники/контент (бэкап посева);
  **не выгружаются** заказы, клиенты, заявки возврата, сессии/листы/журналы
  инвентаризации (тестовые/операционные), promo_codes и admin_users
  (чувствительные). После ручных правок справочников на живой базе аналитик
  перезагружает соответствующий `*_rows.csv` (СВ-06). 152-ФЗ: живая база вне
  России — только тестовые данные, реальные ПДн не вводим.
* **Ключи БД** — только `assets/js/config.js` (публичный anon-ключ в черновике
  — штатно: доступ ограничивает RLS); в отчётах/чатах ключи не цитировать.
* Рабочие документы аналитика (план развития, трекер) — в репозиторий не
  публикуются, кроме лежащих в `workaichat/` по решению аналитика;
  в опубликованных документах упоминаются как рабочие.

## 8. Версионирование и имена файлов

* Точки синхронизации версии (сверяет check-repo v3.1+): SITE_VERSION в
  config.js; шапка README; строка таблицы версий README; техпаспорт (§15 +
  «Версия проекта»); редакция viki-reestr; счётчики БД (таблицы/политики/
  функции/ключи site_content — в техпаспорте); «Следующий инкрементный
  скрипт — N» в supabase/README (синхронно в техпаспорте и README); строка
  check-repo. **SECURITY/LICENSE** — отметка «Версия: смотреть в README.md»
  (контролируется наличие отметки, не версия).
* Имена: `update-vXXX.md` (v + мажор+минор+патч без точек: v0211);
  `otchet-volna-vXXX-DD-MM-YYYY.md` / `otchet-oborot-<тема>-DD-MM-YYYY.md`;
  SQL — `NN_snake_case.sql`; workaichat — транслитерация
  (`ozhidaemye-deystviya.md`); архивы скриптов —
  `supabase/archive/sql-NN-MM-vXYYY.md`.
* Нумерация волн — по плану развития; следующий SQL-скрипт и следующая волна —
  фиксируются в отчёте оборота и supabase/README.

## 9. Чек-лист разработчика перед выдачей пакета

1. Черновик инструкции прошёл решения аналитика (или пункт помечен
   «по рекомендации разработчика»); **после исполнения черновик удалён**
   из `work/draft/`.
2. Смоук на свежем PostgreSQL 15 — N/N PASS; RLS под anon; повторный прогон
   инкремента — no-op; самопроверочные строки совпали дословно.
3. `node --check` изменённых JS; `check-repo.py` — exit 0 (рабочая копия
   и симуляция пакета).
4. Сканы чистые (CJK/`$`/алфавиты/дубли заголовков/первые байты).
5. Дерево §2 инструкции совпадает с фактическим составом пакета (включая
   пометки «УДАЛИТЬ на GitHub»); config.js — точечно, последним; порядок
   загрузки указан.
6. Документы-точки синхронизации обновлены (§2/§8 регламента); fp помечен
   «РЕАЛИЗОВАНО»; viki-reestr — новая редакция; SECURITY/LICENSE/setup-supabase
   — НЕ трогались (кроме случаев смены модели/границ).
7. Один объединённый отчёт оборота написан (§6); список изменений
   `workaichat/` — в тексте ответа.
8. Бэкапы data/ — план выгрузки описан в инструкции §4 п.5 (выгружает аналитик).
