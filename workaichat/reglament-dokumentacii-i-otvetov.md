**Редакция 1.0 · 10.10.2026 · Статус:** рабочий регламент в корне
`workaichat/` (вместе с трекером `ozhidaemye-deystviya.md`); создан по

ведения документов и подготовки пакетов волн, а также формат ответов
ИИ-ассистента (разработчика волн) в чате. Регламент не заменяет источники
(viki-reestr, инструкции update-vXXX, трекер) — при расхождении приоритет
у источника, регламент подлежит правке.

**Основание и источники.** Правила собраны из действующих документов проекта:
`docs/viki-reestr.md` (ред. 3.7 — циклы обновления, фиксированный состав

вносятся отдельной правкой (редакция 1.1+) по предоставлении файла.

## 1. Роли и каналы оборота

| Роль | Кто | Что делает |
|---|---|---|
| Владелец | владелец магазина | решения, ответы на вопросы опросника, контент, приёмка |
| Аналитик | ведущий аналитик (Albert23NO@ya.ru) | задания волн, решения Д#, загрузка пакетов на GitHub, применение SQL на живой базе, документооборот, приёмка с владельцем |
| Разработчик | ИИ-ассистент | исполнение волн: черновик → код/SQL → тесты → документы → отчёт; сверки загрузки |
| Внешний ревьюер | периодически | независимое ревью (отдельный документ на раунд — `docs/review/`) |
| Юрист | с M4 | юридические позиции (гейт M4/первого заказа) |

Каналы: чат (задания аналитика ↔ ответы разработчика), GitHub-репозиторий
(пакеты волн — загружает аналитик через Web UI), GitHub-wiki (записки
аналитика — страница для аналитика, разработчиком не синхронизируется —
решение 06.10.2026), живая база Supabase (скрипты применяет аналитик
в SQL Editor; разработчик сверяет результат через REST).

## 3. Порядок подготовки и исполнения волны

1. **Задание аналитика** — «начинаем волну vX.Y.Z» (цитируется дословно
   в «Основании» отчёта).
2. **Черновик инструкции** — разработчик готовит `work/draft/update-vXXX-chernovik.md`
   (**вне клона**; решение аналитика 09.10.2026 — «сначала черновик»):
   состав волны, открытые вопросы с рекомендациями разработчика (нумерация
   Д#), план смоука, предварительное дерево §2. Статус черновика — в шапке
   (ревизия N; после исполнения — «ИСПОЛНЕН»).
3. **Решения аналитика** — Д1…Дn. Пункты, не вошедшие в ответ, исполняются
   **по рекомендациям разработчика** и помечаются в отчёте (§3 — как Д13–Д15
   волны v0.20.0). Переопределения до старта — принимаются; после старта —
   только следующей волной/патчем.
4. **Исполнение:**
   * SQL — новый инкрементный скрипт с очередного номера (сейчас следующий —
     **33**; номера 06–08, 10–25 не переиспользуются): шапка (цель, версия
     волны, идемпотентность, порядок) + префлайт + самопроверка select'ом
     **точных ожидаемых значений** (строка приводится в скрипте и в инструкции
     §4 дословно); идемпотентность — create if not exists / create or replace /
     on conflict do nothing / drop … if exists; разовые data-операции — с
     guard по старому значению (повторный прогон — no-op);
     **живая база получает только инкременты ≥ 26** (модель F21 — baseline
     не перезапускать); многошаговые записи — одной транзакцией; блокировки —
     FOR UPDATE в детерминированном порядке (F23);
   * фронтенд — vanilla JS без сборки; **чтение страницы — одним бандлом**
     (SECURITY DEFINER RPC, грабля №6 — без N+1); запись каталога/справочников
     в черновике — draft-CRUD напрямую (осознанная граница); утилиты — только
     `util.js` (экранирование, whitelist схем, маски, CSV-защита от формул —
     F32); изменяемые тексты — из `site_content`, без хардкода (правило п.11);
     `config.js` — ключи БД и SITE_VERSION, больше ничего;
   * документы — по §2 регламента; тексты без CJK-вкраплений, без смешения
     алфавитов в идентификаторах, `$` в SQL/MD — только программные правки
     (нечёткие замены дают `$`-коллапс) + скан дублей заголовков.
5. **Верификация разработчика (до отчёта):**
   * прогон всей цепочки скриптов на **свежем PostgreSQL 15** (самопроверки
     всех скриптов — дословно; грабля №15: pglast не проверяет тела
     language-sql функций — прогон обязателен);
   * смоук волны (сценарии S1…Sn + регрессы + RLS под anon + повторный прогон
     инкремента — no-op); драйвер и сценарии — в `workaichat/pgtest/`;
   * `node --check` всех изменённых JS;
   * `python3 tests/check-repo.py` — **exit 0** (в рабочей копии и в
     симуляции пакета на свежем клоне);
   * сканы: CJK — 0; одиночные `$` в supabase/*.sql — 0; смешение алфавитов — 0;
     дубли заголовков MD — 0 (`grep -c '^# '` = 1); первые байты изменённых
     HTML — `<!DOCTYPE html>`.
6. **Отчёт** `workaichat/reports/otchet-volna-vXXX-DD-MM-YYYY.md` (состав — §6
   регламента) → аналитику.
7. **Загрузка аналитиком:** скрипты на живой базе (по инструкции §4 п.1,
   самопроверки сверить до символа) → GitHub Web UI: пакет по §2 инструкции
   (порядок: **скрипты → новые файлы → перезапись → config.js точечно
   последним**) → Pages публикуется автоматически.
8. **Сверка разработчика** в следующем обороте: свежий клон (check-repo,
   состав, маркеры редакций, первые байты) + живой сайт (версия, побайтово
   ключевые файлы) + REST-сверка живой базы → отчёт
   `workaichat/reports/sverka-zagruzki-vXXX-DD-MM-YYYY.md` (находки —
   нумерованные, с критичностью 🔴/🟡/⚪).
9. **Приёмка с владельцем** — чек-лист инструкции §4 п.4 + универсальный
   чек-лист приёмки (по запросу аналитика). Замечания приёмки → вики-записки
   → `docs/priemka/priemka-v0XX.md` → следующие волны.

## 4. Формат инструкции `docs/update/update-vXXX.md` (фиксированный состав — viki-reestr §2.2, образец v0141/v0200)

Шапка: заголовок «Инструкция по обновлению черновика до vX.Y.Z-draft (волна …)»;
«Куда смотреть» (что за волна); «Основание» (fp №, план развития §, требования
владельца дословно, решения Д# с датами, черновик work/draft/ — ревизия);
«Версия сайта» (SITE_VERSION + предупреждение: в GitHub-копии config.js
править **точечно, только эту строку** — в файле настоящие ключи БД).

Разделы:
1. **Что изменилось (состав волны)** — 1.0 решения до старта (Д# — дословно/
   сводка); 1.1 база (скрипты: состав, самопроверочные строки, счётчики
   таблиц/политик/функций/скриптов, следующий номер, бэкапы data/); 1.2+ —
   админка/витрина по страницам и модулям; тесты; документы.
2. **Файлы для загрузки в репозиторий** — дерево **от корня клона, с
   углублением в папки** (грабля №18; эталон — update-v0170 §2); каждое
   дерево-элемент с пометкой: `(НОВЫЙ)` / `(перезапись; что меняет)` /
   `(⚠ ТОЧЕЧНО: только строка SITE_VERSION → '…'; ключи БД не трогать)`;
   постоянные напоминания: SITE_VERSION в GitHub-копии config.js;
   синхронизация docs/plan/*.md (правило v0.14.1); пути docs/ — только по
   структуре подпапок; итог — «Всего: N новых и M перезаписываемых» +
   что НЕ затрагивается + оговорка «изменения `workaichat/` — вне этой
   инструкции (список — в сообщении разработчика)». Перед деревом — порядок:
   **скрипты на живой базе → новые файлы → перезапись → config.js точечно**.
3. **Версия (точки синхронизации)** — таблица: config.js, шапки README/
   SECURITY/LICENSE, строка таблицы версий README, техпаспорт, viki-reestr
   (редакция), счётчики БД, строка check-repo.
4. **База, публикация и проверка** — п.1 скрипты на живой базе (номера,
   порядок, ожидаемые строки самопроверок дословно, оговорки F21/одноразовости);
   п.2 Pages; п.3 отсылка к §2; п.4 контроль после загрузки (свежий клон —
   check-repo exit 0; первые байты HTML — грабля №17в; REST-сверка — конкретные
   ожидаемые значения; живой сайт — версия; ручные сценарии — нумерованные,
   каждый «глазами»); п.5 бэкапы data/ (что выгружает аналитик, что НЕ
   выгружается — чувствительное и операционное).
5. **Финальная проверка (выполнена разработчиком до загрузки)** — цепочка/
   смоук/RLS/no-op/node --check/check-repo/сканы — фактические результаты.
6. **Открытые пункты (не входят в волну)** — нумерованные, со сроками/адресатами.
7. **Урок для регламента** — если волна дала новую граблю (номер — следующий
   по реестру; фиксация — здесь + viki-reestr + этот регламент).
Приложения: **А** — смоук (таблица сценариев и результатов); **Б** — формы
RPC/схем фактические (для сверки и будущей приёмки).

## 5. Формат ответа ИИ (разработчика) в чате

1. **Состав ответа:** (а) что сделано — кратко, с ключевыми результатами
   верификации (цифры: смоук N/N, check-repo exit 0, счётчики); (б) **список
   изменённых файлов** — репозиторий (по папкам) и **отдельно `workaichat/`**
   (изменения workaichat перечисляются **только в теле текстового ответа**,
   в документах и отчётах не упоминаются — указание аналитика 10.10.2026);
   (в) «ожидает от аналитика» — нумерованный список (скрипты, загрузка,
   решения, подтверждения); (г) вопросы — если есть.
2. **Вопросы — до старта, одним сообщением** (консолидированно; не серией
   уточнений по ходу исполнения). Открытые пункты черновика — нумерацией Д#
   с рекомендациями разработчика.
3. **Без дублирования документов:** в чате — выжимка и указатели (файл §п.),
   не пересказ разделов. Цитаты заданий/решений аналитика — дословно
   (в отчёте — блок «Основание»).
4. **Отчёты — только действия и изменения** (заметки аналитика §6 п.2,
   ред. 06.10.2026): описания ревизий в рабочих файлах не ведутся (история —
   в архивных копиях и viki-reestr); версия/редакция — в шапке.
5. **Оформление:** русский язык; даты — ДД.ММ.ГГГГ; номера версий — SemVer
   0.x (MINOR — волна, PATCH — гигиена, без функционала); идентификаторы
   пунктов — устойчивые (АН-/ВЛ-/ЮР-/СВ-/Д#/F##/грабля №N — не перенумеровываются,
   закрытые не переиспользуются); статусы — 🔴/🟡/⚪/✅ (семантика — трекер
   «Как читать»).
6. **Что не делается без явного указания аналитика:** публикация/коммиты
   на GitHub (загружает аналитик); правка замороженных [З] документов;
   обновление универсального чек-листа приёмки; архивация трекера; удаление
   файлов; изменения живой базы (разработчик — только чтение через REST).

## 6. Формат отчётов (`workaichat/reports/`)

**Отчёт волны** `otchet-volna-vXXX-DD-MM-YYYY.md`:
шапка (Разработчик; Основание — дословная цитата задания; Тип волны
MINOR/PATCH, оценка S/M/L; Версия рабочей копии; статус пакета — «ждёт
загрузки»); §0 до старта — сверка GitHub/живой базы, если обороту предшествовали
правки аналитика (находки — закрыта/не закрыта); §1 состав исполнения
(новые/изменённые файлы репозитория + документы оборота; workaichat — списком
в тексте ответа); §2 верификация (цепочка скриптов и самопроверки, смоук N/N,
RLS, no-op, node --check, check-repo vX.Y — exit 0, сканы); §3 решения и
отметки (Д# исполненные/по рекомендациям; что не менялось и почему; открытое
до приёмки/боевых вех); §4 ожидает от аналитика (нумерованно: скрипты →
загрузка → контроль → приёмка → следующая волна).

**Отчёт сверки** `sverka-zagruzki-vXXX-DD-MM-YYYY.md`: шапка (Основание —
дословно; Метод — клон/HEAD/инструменты); §1 подтверждено (пакет, Pages,
живая база — таблицей ожидание/факт); §2 находки (нумерованные, критичность
🔴 требует правки / 🟡 требуется диагностика или решение / ⚪ информационная;
для каждой — суть, анализ, действие); §3 ожидает от аналитика; приложения
(эталоны, диагностические запросы).

## 7. Гигиена файлов и данных

* **Грабля №17в** (решение 10.10.2026): ведущие CRLF-строки, добавляемые
  GitHub Web UI загружаемым HTML/CSS, временно оставляем; проверка первых
  значимых байтов после каждой загрузки; **перед M1 — очистка** (пакет АН-29).
* **Бинарные файлы:** после загрузки — контроль размеров (грабля №17;

* **data/:** выгружаются только справочники/контент (бэкап посева);
  **не выгружаются** заказы, клиенты, заявки возврата, сессии/листы/журналы
  инвентаризации (тестовые/операционные), promo_codes и admin_users
  (чувствительные). 152-ФЗ: живая база вне России — только тестовые данные,
  реальные ПДн не вводим.
* **Ключи БД** — только `assets/js/config.js` (публичный anon-ключ в черновике
  — штатно: доступ ограничивает RLS); в отчётах/чатах ключи не цитировать.
* Рабочие документы аналитика (план развития, черновики work/draft/, трекер) —
  в репозиторий не публикуются, кроме лежащих в `workaichat/` по решению
  аналитика; в опубликованных документах упоминаются как рабочие.
