### 0.1. Сильные решения — переносим в новый проект как паттерны

| Паттерн из учебного проекта | Почему ценен | Как используем |
|---|---|---|
| Заказ только через серверную функцию `create_order()` | Цены берёт сервер — подмена стоимости из консоли невозможна | Тот же принцип: единственный API-эндпоинт создания заказа, цены и остатки сверяются на сервере |

| Локальная библиотека вместо чужого CDN (`assets/supabase.min.js`) | Устойчивость к недоступности CDN | Возводим в принцип: **ноль внешних CDN**, всё вендорим |

| Не берём | Причина | Чем заменяем |
|---|---|---|
| Supabase (БД, Auth, Storage, RLS) | Серверы за рубежом — с 01.07.2025 ч. 5 ст. 18 152-ФЗ прямо запрещает первичный сбор ПДн граждан РФ в базы вне России | Российские решения — раздел 2 отчёта |
| Брендбук (неон #FF2D95, фиолетовый, свечения) | Другой бизнес: неон — для молодёжного handmade, не для премиум-сегмента | Новая айдентика «quiet luxury» — раздел 4 |

| `custom-order.html` и таблица `custom_orders` | Кастом-изготовление не входит в модель магазина | Не создаём; если появится «подбор образа/аромата» — отдельная фича позже |
| Фото по hotlink-ссылкам из ВК (`sun9-*.vkuserphoto.ru`) | Ссылки содержат подписи и устаревают; для реальной торговли ненадёжно и юридически спорно | Собственное хранилище картинок — раздел 2 |
| Один файл `index.html` на 251 КБ | В самом учебном проекте это записано в TODO («разнести на файлы») | Раздельные файлы: css/, js/, страницы |
| Авторизация «SHA-256 хеш в sessionStorage» | Учебное упрощение; в паспорте честно перечислены 5 отсутствующих механизмов | Продвинутая модель: сессии, роли, 2FA, rate-limit, аудит — п. 1.7 |
| GitHub Pages как хостинг магазина | В июне–июле 2026 фиксировались массовые сбои доступа к GitHub из России; для продающего сайта это риск | Российский хостинг; GitHub остаётся для кода и CI |
| Tailwind через CDN | Зависимость от зарубежного CDN + «внешний вид» премиума требует уникальности | Собственный CSS на дизайн-токенах (переменные), шрифты — локально woff2 |

### 0.3. Вывод по учебному проекту

Проект дал отличную инженерную базу: статусная модель, серверное ценообразование,
аудит, документация, миграции. Новый проект переиспользует **архитектурные паттерны**,
но полностью меняет **инфраструктуру (РФ), идентичность (премиум) и модель доступа (настоящая аутентификация)**.

## 1. План разработки статичного сайта на HTML

### 1.1. Архитектура

Принцип тот же, что в учебном проекте: **статический фронтенд + тонкий серверный слой для данных**.
Никаких сборок, фреймворков, Node.js на проде — чистые HTML5 / CSS3 / vanilla JS (ES6+),
как ты и просила («статичный сайт на html»).

```
        Покупатель                         Владелец магазина
             │                                     │
             ▼                                     ▼
 ┌──────────────────────────┐        ┌──────────────────────────────┐
 │  Статические страницы     │        │  Админка (тоже статические    │
 │  index.html, privacy.html │        │  страницы admin/*.html,      │
 │  (HTML/CSS/JS без сборки) │        │  вход по логину+паролю+2FA)  │
 └────────────┬─────────────┘        └──────────────┬───────────────┘
              │  fetch() → JSON API (same-origin)   │
              ▼                                     ▼
 ┌────────────────────────────────────────────────────────────────┐
 │  Серверный слой в РФ (вариант A: Beget free — PHP 8 + MySQL;    │
 │  вариант B: Yandex Cloud — API Gateway + Functions + YDB)       │
 │  • единственная точка записи заказов (цены/остатки — с сервера) │
 │  • сессии и роли админки, аудит, rate-limit                     │
 │  • уведомления: Telegram-бот + e-mail                           │
 └──────────────┬──────────────────────────┬──────────────────────┘
                ▼                          ▼
        База данных (РФ)           Хранилище фото (РФ)
        заказы, каталог, юзеры     WebP-фото товаров
```

**Ключевое отличие от учебного проекта:** фронтенд и API на одном домене (same-origin) —
не нужен CORS, работают обычные сессионные cookie (HttpOnly), а база данных вообще
не «торчит» в интернет: единственный вход — через API-слой. Это строже, чем PostgREST+RLS.

**Варианты серверного слоя** (детальное сравнение — раздел 2):
- **Вариант A (рекомендую):** бесплатный хостинг Beget — статика сайта + PHP-API + MySQL + фото на одном аккаунте, бесплатно и бессрочно, дата-центры в РФ, автоматические бэкапы.
- **Вариант B:** Yandex Cloud serverless — API Gateway + Cloud Functions + YDB (всё в бесплатных лимитах), фото в Yandex Object Storage. Современнее и масштабируемее, но больше кода и нужна привязка карты для биллинга.

План ниже написан так, чтобы страницы и контракт API не зависели от выбора варианта:
различается только папка `api/` (PHP) или набор функций (Yandex).

#### privacy.html — политика обработки ПДн

Структура учебного проекта (12 разделов) — хорошая и законная по составу, берём как
шаблон **структуры**, но полностью переписываем содержание под нового оператора:
общие положения (реквизиты `[ИП/ООО]`), состав данных (ФИО, телефон, e-mail, адрес
доставки, cookie, метрика), цели (исполнение договора купли-продажи — с момента заказа),
правовые основания, **хранение только на серверах в РФ (хостер: Beget/Яндекс, указываем
наименование и адрес ДЦ)**, сроки (например, 1 год после последнего заказа или 5 лет по
требованиям бухгалтерии — фиксируем в волне 0), третьи лица (хостер, служба доставки,
Telegram-уведомления — по минимуму), cookie и Яндекс.Метрика, права субъекта (доступ,
уточнение, блокирование, уничтожение — порядок по ст. 14 152-ФЗ), дети (не собираем),
контакты оператора и ответственного за обработку ПДн, порядок изменения политики.
Отдельно: **уведомление Роскомнадзора о начале обработки ПДн** (ст. 22) — до запуска.

#### admin/login.html, admin/orders.html, admin/stats.html

- **login.html:** логин + пароль + код 2FA (TOTP); ссылка «Забыли пароль» (сброс по e-mail одноразовым токеном); сообщение о блокировке после N неудачных попыток; mobile-friendly.
- **orders.html (панель заказов):** только ПК-ориентированный интерфейс как в учебном проекте, но с полным CRUD-лайтом: список с фильтрами (статус, дата, оплата, доставка, поиск по ФИО/телефону/номеру), пагинация, карточка заказа (позиции с размерами, снапшоты цен, оба комментария, доставка, история статусов с ролями), **смена статуса** с проверкой разрешённых переходов, признак оплаты `is_paid` с датой, трек-номер, маскирование контактов + «глазик», экспорт в CSV (BOM, `;`), аудит всех действий.
- **stats.html (статистика):** KPI-карточки (заказы за период, выручка оформленных заявок, оплаченная выручка, средний чек, конверсия воронки, доля отмен); графики: заказы/выручка по дням-неделям-месяцам, воронка статусов, топ товаров и брендов, распределение способов оплаты и доставки, эффективность промокодов; выбор периода (7/30/90 дней, произвольный); экспорт сводки в CSV. Графики — вендоренный Chart.js (без CDN).

### 1.4. Модель данных (адаптация учебной схемы под одежду и парфюмерию)

Учебная схема (17 таблиц) хорошо спроектирована — берём за основу и дорабатываем
под новую предметную область. Главное отличие: у одежды есть **размеры**, у парфюмерии —
**объёмы**, поэтому появляется слой вариантов (SKU).

| Таблица | Назначение | Новое/изменённое vs учебная схема |
|---|---|---|
| `brands` | Бренды (если магазин мультибрендовый) | **новая**; если бренд один — вырождается в поле |
| `categories` | Категории: одежда (подкатегории), парфюмерия | как в учебной |
| `products` | Товар: артикул, название, описание, базовая цена, состав, страна, `is_active` | + `brand_id`, + поля состава/страны |
| `product_variants` | **новая**: SKU = товар + размер/объём + остаток `stock_qty` | ключевое добавление для одежды/духов |
| `product_images` | Галерея: url, порядок, alt-текст | как в учебной |
| `site_content` | Тексты/картинки сайта по ключам | как в учебной |
| `orders` | Заказ: клиент (имя, телефон, e-mail, город, адрес/ПВЗ), статус, оплата, доставка, суммы, промокод | + адресные поля; без `custom_*` |
| `order_items` | Позиции: `product_id`, **`variant_id`**, количество, снапшоты цены/названия/размера | + variant, + снапшот размера |
| `order_statuses` + `status_transitions` + `order_status_history` | Статусная модель и аудит | как в учебной, но БЕЗ статуса «Оплачен» (удалён в черновике v0.2.0, ревизия F47): new → confirmed → packing → shipped → delivered; cancelled; returned; оплата — признак `is_paid` + `paid_at` на любом этапе |
| `payment_methods`, `payments` | Способы оплаты и факты оплат | как в учебной |
| `delivery_methods`, `deliveries` | Способы доставки, трек-номера, ПВЗ | как в учебной |
| `promo_codes` | Промокоды (закрыты от публичного чтения, проверка на сервере) | как в учебной |
| `users` | **новая**: админы — логин, хеш пароля (bcrypt/argon2id), роль (owner/manager/viewer), 2FA-секрет, `is_active` | заменяет `admin_credentials` с одним паролем |
| `sessions` | **новая**: серверные сессии — токен-хеш, user_id, created/expires, user-agent, ip, отзыв | заменяет sessionStorage-хеш |
| `login_attempts` | **новая**: попытки входа для rate-limit и блокировок | расширяет `admin_login_log` |
| `audit_log` | **новая**: действия админов (смена статуса, экспорт, правка товара): кто, что, когда, до/после | расширяет историю статусов |
| `reviews` | Отзывы с премодерацией | фаза 2 (после запуска) |

Доступ: в варианте A (PHP+MySQL) «RLS» заменяется тем, что **БД вообще не доступна из
интернета** — все запросы идут через PHP с подготовленными выражениями (PDO prepared
statements) и проверкой роли в сессии. В варианте B (Yandex) — функции с IAM и
валидацией токенов.

### 1.5. Контракт API (единый для обоих вариантов серверного слоя)

| Метод и путь | Кто | Что делает |
|---|---|---|
| `GET /api/catalog?category=&brand=&sort=` | все | Категории, бренды, активные товары с вариантами и фото |
| `GET /api/content` | все | Ключи `site_content` для подстановки текстов; + текущая версия политики ПДн `policy_version` (ревизия F48) |
| `POST /api/orders` | все | Создание заказа: сервер сверяет цены/остатки, валидирует (имя, ≥1 контакт, количество 1–99, ≤50 позиций), rate-limit «не более 3 заказов за 10 минут» по нормализованному телефону/e-mail, пишет заказ+позиции+доставку+историю+клиента атомарно, шлёт уведомление владельцу; возвращает только номер и суммы. | `POST /api/promo/check` | все | Проверка промокода (таблица не читается публично) |
| `POST /api/auth/login` | админ | Логин+пароль → проверка rate-limit → выдача сессионной cookie; если у юзера включена 2FA — временный «pre-auth» токен и требование кода |
| `POST /api/auth/2fa` | админ | Подтверждение TOTP-кода → полноценная сессия |
| `POST /api/auth/logout` | админ | Уничтожение сессии на сервере |
| `POST /api/auth/reset/request` / `confirm` | админ | Сброс пароля: одноразовый токен на e-mail, срок 30 мин |

| `POST /api/admin/orders/{id}/paid` | owner/manager | Признак оплаты + дата |
| `GET /api/admin/stats?period=` | owner/viewer | Агрегаты статистики (все суммы считаются на сервере) |

Все admin-эндпоинты: только HTTPS, только активная сессия с ролью, CSRF-токен для
мутирующих запросов, единый формат ошибок, лимит размера тела запроса.

**Агрегирующие эндпоинты (ревизия F46, опыт черновика v0.5–v0.14):** черновик
лечил очередь соединений Supabase RPC-бандлами — в бою те же контракты:
`GET /api/storefront` (каталог + справочники + тексты + луки одним ответом,
прототип — `draft_storefront_bundle()`), `GET /api/admin/overview`
(`draft_admin_bundle`), `GET /api/admin/assembly` (`draft_assembly_bundle`),
`GET /api/admin/clients` (`draft_clients_bundle`). Состав полей переносится
из черновых бандлов без переизобретения.

### 1.7. Продвинутая модель авторизации (то, чего не хватало в учебном проекте)

Прямое сопоставление «учебная модель → новая модель»:

| Механизм | Учебный проект (честно описанные границы) | Новый проект |
|---|---|---|
| Хранение пароля | SHA-256 хеш (без соли) в `admin_credentials` | `password_hash()`: bcrypt cost=12 или argon2id (соль автоматически), отдельный хеш на пользователя |
| Передача при входе | Хеш считается в браузере и ходит по сети как «пароль» | Пароль передаётся один раз по HTTPS, на сервере сравнивается с хешем; хеш никогда не покидает сервер |
| Сессия | `sessionStorage` с хешем — «вкладка = доступ», нет серверного состояния | Серверная сессия: случайный токен (256 бит), в БД — его хеш, user_id, срок; cookie `HttpOnly; Secure; SameSite=Lax; Path=/`; idle-timeout 30 мин, абсолютный срок 12 ч; кнопка «завершить все сессии» |
| Пользователи и роли | Один пароль на всех | Таблица `users`: owner (всё + управление юзерами), manager (заказы, без статистики выручки и настроек — состав прав уточняем в волне 0), viewer (только статистика); смена роли только owner'ом |
| Брутфорс | Серверного rate-limit нет — «подбор теоретически возможен» | `login_attempts`: прогрессивная задержка, после 5 неудач — блокировка логина на 15 мин + после 20 — алерт владельцу (Telegram); отдельный лимит на сброс пароля |
| 2FA | Нет | TOTP (RFC 6238): включается обязательно для owner, рекомендуется остальным; работает с Яндекс.Ключ/Google Authenticator; резервные коды (10 одноразовых) |
| Журналирование | `admin_login_log` (уже хорошо) | Расширяем: входы (успех/неуспех, ip, user-agent, какой юзер), `audit_log` на все изменения (статусы, оплаты, правки каталога, экспорт CSV — экспорт тоже событие!) |
| Восстановление доступа | Только через SQL Editor | Сброс пароля одноразовым токеном на e-mail (30 мин, одноразовый, хеш в БД) + аварийный путь через хостинг-панель, если e-mail недоступен |
| CSRF | Не применимо (нет cookie-сессий) | Обязателен: CSRF-токен на все мутирующие запросы админки, `SameSite=Lax` как второй рубеж |
| Клиентская защита | Экранирование вывода (уже есть) | Сохраняем экранирование всего вывода + CSP-заголовок (default-src 'self'), X-Frame-Options DENY, X-Content-Type-Options nosniff, Referrer-Policy |

Плюс организационное: пароль owner'а ≥16 символов (генерируем при настройке),
секреты (пароль БД, токен Telegram-бота, ключи API) — только в `config.php`/переменных
хостинга, **никогда в git** (в репозитории — `config.example.php`); `.gitignore` с первого коммита.

- **Версионирование:** SemVer, версия в футере всех страниц, CHANGELOG.md, история версий в техпаспорте.
- **Документация:** техпаспорт (архитектура, схема БД, пути пользователя, безопасность) обновляется в каждой волне; планы фич в `docs/plans/` до реализации; ADR на каждое значимое решение (инфраструктура, авторизация, дизайн).
- **Миграции БД:** нумерованные идемпотентные скрипты `db/NN_*.sql`, реестр в `db/README.md`, запрет разрушающих операций без пометки DANGER и бэкапа (правила учебного supabase/README переносим дословно — они отличные).
- **Тесты:** SQL-тесты (прогон схемы и бизнес-правил: подмена цены, запрет перехода статусов, лимит заказов), jsdom-тесты фронтовой логики (корзина, валидация формы), ручной чек-лист приёмки каждой волны, чек-лист безопасности перед v1.0.

- **Бэкапы:** на Beget автоматические (проверяем восстановлением в волне 6); дополнительно — еженедельный дамп БД себе (скачать SQL + CSV) — практика учебного проекта «Download data to CSV перед импортом» становится регламентом.

### 1.9. Юридический минимум реального магазина (чек-лист, не юрконсультация)

1. **Статус продавца:** для перепродажи товаров самозанятость (НПД) не подходит — нужны ИП (УСН) или ООО. Это влияет на acquiring и чеки. *Уточнить у владельца — вопрос №2 в разделе 5.*
2. **Сведения о продавце на сайте:** наименование, ОГРНИП/ОГРН, ИНН, адрес — обязательны для дистанционной торговли (ст. 26.1 ЗоЗПП, Правила продажи № 2463). Размещаем в «Условиях заказа» и футере.
3. **152-ФЗ:** политика обработки ПДн на сайте (privacy.html); чекбокс согласия в формах; **уведомление Роскомнадзора о начале обработки** (ст. 22, подаётся через pd.rkn.gov.ru до сбора данных); локализация баз в РФ (ст. 18 ч. 5) — обеспечивается выбором хостинга; при утечке — уведомление РКН в 24 ч/72 ч (ст. 21) — процедура описана в SECURITY.md.
4. **Дистанционная продажа:** право отказа от товара — 7 дней после передачи (ст. 26.1 ЗоЗПП); информация о порядке и сроках возврата — в «Условиях заказа». Нюансы невозврата парфюмерии именно при дистанционной продаже спорны — формулировки раздела возврата согласовать с владельцем (и, в идеале, с юристом).
5. **Чеки (54-ФЗ):** при онлайн-оплате нужен чек — либо онлайн-касса, либо сервис эквайринга с авточеками (ЮKassa, Robokassa). В v1 при ручной оплате переводом чеки пробивает сам продавец — фиксируем ответственность владельца.
6. **Маркировка «Честный ЗНАК»:** парфюмерия и значительная часть одежды — маркируемые товарные группы (календарь поэтапно расширялся в 2024–2026 гг.); продажа маркируемого товара требует регистрации в системе и выбытия кодов. *Проверить по его конкретным товарным группам — вопрос №3.*
7. **Cookie/метрика:** Яндекс.Метрика ставится с уведомлением в cookie-баннере и разделе 8 политики ПДн.
8. **Домен:** для доверия премиум-аудитории — собственный .ru-домен (~200–400 ₽/год, единственная практически неизбежная статья расходов); на этапе разработки достаточно бесплатного поддомена хостера.

## 2. База данных и хранилище картинок: бесплатные решения с серверами в РФ

### 2.1. Правовая рамка (почему Supabase больше нельзя)

С 01.07.2025 действует обновлённая **ч. 5 ст. 18 152-ФЗ**: первичный сбор персональных
данных граждан РФ запрещён с использованием баз, находящихся за пределами России.
Заказы (ФИО, телефон, e-mail, адрес) — это ПДн → база заказов обязана стоять в РФ.
Фотографии товаров ПДн не являются — для них «российскость» сервера не обязательна
юридически, но желательна по скорости и надёжности для российской аудитории.

### 2.2. Свободные (бесплатные) варианты — сравнение

| Критерий | **Beget FreeHosting** (рекомендую) | SpaceWeb free | Яндекс Cloud serverless | VK Cloud | Supabase (для справки) |
|---|---|---|---|---|---|

### 2.3. Рекомендация по базе данных

**Вариант A (основной): Beget FreeHosting.**
Почему: единственный вариант, где бесплатно и бессрочно в одном месте в РФ получают
сайт + API + MySQL + хранилище фото + SSL + автоматические бэкапы, без привязки карты.
Same-origin убирает CORS и упрощает сессионные cookie (важно для продвинутой модели
авторизации из п. 1.7). Ограничения (1 сайт, 1 ГБ, 1 БД, 10 CP, без поддержки) для
витрины премиум-сегмента с ручным приёмом оплаты — достаточны на год вперёд.
Путь роста без переделки фронта: платный тариф Beget (от ~420 ₽/мес) → VPS с
self-hosted Supabase (вернём привычные по учебному проекту PostgREST/Auth/Storage,
но на российском сервере, ~300–600 ₽/мес) → Yandex Cloud.

**Вариант B (запасной/масштабирование): Yandex Cloud serverless.**
Связка API Gateway (100 тыс. запросов/мес) + Cloud Functions (1 млн вызовов/мес) +
YDB serverless (1 млн RU, 1 ГБ/мес) + Object Storage (1 ГБ, 100 тыс. GET/мес) +
Postbox (2000 писем/мес) + SmartCaptcha (10 тыс./мес) + Cloud Logging (5 ГБ) — всё в
постоянных бесплатных лимитах, ДЦ в РФ. Дополнительно грант 4000 ₽ (физлицо) /
10 000 ₽ (юрлицо) на старте — на нём можно первые месяцы гонять даже Managed
PostgreSQL. Минусы: нужна карта для биллинг-аккаунта, API полностью пишем сами,
YDB — не PostgreSQL (другой диалект, нет привычных stored procedures), статический
сайт придётся хостить отдельно (тот же Beget) → появляется CORS и аккуратная работа
с токенами вместо cookie.

**Вердикт:** стартуем на варианте A; контракт API (п. 1.5) спроектирован так, что
переезд на B — это замена папки `api/`, а не переписка сайта.

7. **Кто наполняет каталог:** владелец сам через CSV/админку, или первая загрузка на мне по его материалам? Сколько товаров на старте (от этого считаем квоту фото)?
8. **Роли в админке:** кто кроме владельца будет пользоваться (ты как аналитик-наблюдатель? менеджер по доставке)? Нужен ли viewer-доступ только к статистике?
9. **Репозиторий:** приватный (рекомендую, см. раздел 3) или публичный-портфолио?
10. **Домен:** покупаем .ru сразу (данные владельца для регистрации) или стартуем на поддомене хостера?
