# План перевода Sisku v0.3.0-draft в боевой магазин

**Дата:** 20.09.2026 · **Версия документа:** 1.0.0
**Исходное состояние:** черновой макет `sisku-draft` v0.3.0-draft (GitHub Pages + Supabase `sisku-draft`, админка без пароля)
**Целевое состояние:** боевой интернет-магазин `[БРЕНД]` v1.0.0 (российский хостинг, настоящая авторизация, юридический контур, реальный контент)
**Связанные документы:** `otchet.md` (план с нуля, волны, авторизация п. 1.7, юрминимум п. 1.9), `drafts/README|LICENSE|SECURITY`

Главный принцип: **черновик доказал дизайн и UX — их не переизобретаем.** Переносим всё, что
работает визуально и логически; переписываем только слой данных и доступа; с нуля строим
то, чего в черновике сознательно не было (авторизация, юрконтур, оплаты, боевой контент).

## 4. Что разрабатываем с нуля

### 4.1. Серверный слой (вариант A: Beget, PHP 8 + MySQL)

```
api/
  bootstrap.php        PDO (utf8mb4, ERRMODE_EXCEPTION), сессия, заголовки безопасности, роутер
  middleware.php       ACL по таблице маршрутов, rate-limit, CSRF для мутаций, JSON-ошибки
  catalog.php  content.php  order.php  promo_check.php (фаза 2)
  auth/ login.php 2fa.php logout.php reset_request.php reset_confirm.php sessions.php
  admin/ orders.php order.php order_status.php order_paid.php stats.php users.php audit.php
  notify/ telegram.php mail.php
```
Заголовки на всех ответах: `Strict-Transport-Security`, `X-Content-Type-Options: nosniff`,
`X-Frame-Options: DENY`, `Referrer-Policy`, `Permissions-Policy`, CSP `default-src 'self'`.
Сессия: `session_set_cookie_params(['httponly'=>true,'secure'=>true,'samesite'=>'Lax'])`.

### 4.2. Новые таблицы БД (сверх портируемых)

| Таблица | Назначение | Ключевые поля |
|---|---|---|
| `users` | администраторы | `login`, `password_hash` (bcrypt cost 12 / argon2id), `role` (owner/manager/viewer), `totp_secret`, `is_active` |
| `sessions` | серверные сессии | `token_hash` (SHA-256 токена), `user_id`, `created_at`, `expires_at`, `last_seen`, `user_agent`, `ip` |
| `login_attempts` | rate-limit/блокировки | `login`, `ip`, `success`, `attempted_at` |
| `audit_log` | аудит действий | `user_id`, `action`, `entity`, `entity_id`, `before_json`, `after_json`, `ip`, `created_at` |
| `consents` | журнал согласий на ПДн | `order_id`, `policy_version`, `consent_at`, `ip`, `user_agent` |
| `payments_log` | фазa 2: события эквайринга | `order_id`, `provider`, `transaction_id`, `amount`, `status`, `raw_json`, `created_at` |

Портируемые из черновика: `brands, categories, products, product_variants, site_content,
order_statuses, status_transitions, payment_methods, delivery_methods, orders, order_items,
deliveries, order_status_history`. В `orders` добавляются `consent_id` (связь с журналом
согласий) и `customer_city` отдельно от адреса (для статистики по географии, фаза 2).

### 4.3. Авторизация (спецификация — по отчёту п. 1.7, здесь суть)

- Логин+пароль → проверка по `login_attempts` (5 неудач → 15 мин блок, 20 → алерт владельцу) → `password_verify` → если включена 2FA: pre-auth токен (5 мин) → TOTP (`RFC 6238`, окно ±1) или резервный код → выдача сессии (токен 256 бит в cookie, в БД — хеш).
- Сессии: idle 30 мин, абсолют 12 ч, список активных сессий в админке с возможностью отозвать; «завершить все сессии».
- Роли: `owner` (всё + users), `manager` (заказы и статусы), `viewer` (только статистика, контакты маскируются сервером).
- Сброс пароля: одноразовый токен на e-mail, 30 мин, хранится хешем.
- Всё журналируется в `login_attempts`/`audit_log`.
- Новые экраны: `admin/login.html` (логин → 2FA), блок «Пользователи и сессии» в админке (owner).

### 4.4. Уведомления

- Telegram-бот: новый заказ (состав, сумма, контакты), смена статуса, алерты безопасности; токен бота — только в конфиге сервера.
- E-mail покупателю: подтверждение заказа с номером (v1 — через SMTP хостера или Yandex Postbox; содержание без ПДн сверх необходимых).

### 4.5. Юридический контур (по отчёту п. 1.9, состав работ)

1. `privacy.html` боевого оператора (структура из 12 разделов черновика-заготовки `new-shop-plan/drafts` не используется напрямую — берём фактическую структуру `privacy.html` учебного проекта с новыми реквизитами): реквизиты, состав данных, цели, основания, хранение в РФ (наименование хостера и ДЦ), сроки, третьи лица (хостер, доставка, платёжный провайдер), cookie/Метрика, права субъекта, контакты ответственного.
2. Чекбокс согласия в форме заказа (обязательный) + запись в `consents` с версией политики.
3. `offer.html` — публичная оферта; блок «Сведения о продавце» (наименование, ОГРНИП, ИНН) в «Условиях заказа» и футере.
4. Правила возврата в «Условиях заказа» (7 дней, ст. 26.1 ЗоЗПП; формулировки по парфюмерии согласовать).
5. Уведомление Роскомнадзора (ст. 22) до начала сбора данных; процедура 24/72 ч в боевом SECURITY.md.
6. Чеки: v1 ручная оплата — продавец пробивает чек сам (памятка в регламенте); фаза 2 — эквайринг с авточеками.
7. Проверка маркировки «Честный ЗНАК» по фактическим товарным группам владельца.
8. Cookie-баннер под Яндекс.Метрику.

### 4.6. Оплаты (фаза 2, после v1.0)

Эквайринг (ЮKassa/Robokassa/CloudPayments — по статусу продавца): страница/ссылка на оплату
из карточки заказа, вебхук → `payments_log` + авто-`is_paid` + смена статуса по модели;
возвраты через API провайдера. До этого действует ручная схема черновика (СБП/перевод +
кнопка «Отметить оплаченным»), но с регламентом чеков из п. 4.5.

### 4.7. Эксплуатация

- Деплой: GitHub Actions → SFTP на Beget (секреты в GitHub Secrets), либо ручная загрузка по инструкции; миграции БД — вручную из `db/` по реестру (как в черновике).
- Бэкапы: автоматические бэкапы хостера + еженедельный самостоятельный дамп MySQL и выгрузка фото; раз в квартал — учебное восстановление.
- Мониторинг: аптайм-пинг (uptime-сервис), ошибки PHP → Telegram, раз в месяц ревизия сессий/пользователей/журнала входов.
- SEO/аналитика: meta/OG per page, `sitemap.xml`, `robots.txt`, Webmaster + Метрика, микроразметка Product/Offer (фаза 2).

## 6. Перенос данных и откат

- **Каталог:** мастер-источник — `data/*.csv` черновика (заменить артикулы/бренды на боевые) → импорт в MySQL скриптом; AI-фото не переносятся.
- **Заказы черновика:** не переносятся (тестовые ПДн-заглушки); Supabase-проект после паузы живёт 30 дней как страховка, затем удаляется вместе с данными.
- **site_content:** ключи переносятся 1:1, значения заменяются боевыми текстами.
- **Откат боя:** DNS обратно на заглушку «сайт скоро откроется», боевой API в read-only (флаг в конфиге), витрина отдаёт кэш каталога; данные не теряются (MySQL + дампы).

## 7. Риски миграции

| Риск | Мера |
|---|---|
| Владелец задерживает контент-пакет (фото премиум-класса — критично) | M1–M4 не зависят от контента; M5 стартует по факту фото |
| Ошибки порта схемы Postgres→MySQL (типы, CHECK, транзакции) | SQL-тесты бизнес-правил из черновика переносятся вместе с логикой; прогон на реальном MySQL в CI |
| Беget free-лимиты на боевом трафике | мониторинг квот; плановый апгрейд тарифа при >10–15 заказов/день (≈420 ₽/мес) без изменения кода |
| Юридические формулировки (возврат парфюмерии, оферта) | согласование с владельцем, при споре — платная консультация юриста (точечно) |
| Один администратор (bus-factor) | второй пользователь manager + документированный аварийный доступ через панель хостера |
