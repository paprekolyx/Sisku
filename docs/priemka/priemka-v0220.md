## 1. Постатейная обработка (10 пунктов записок 18.10.2026)

**П1. Статистика → Клиенты: нет обратной навигации из карточки клиента.**
Код: `admin.js:916–918` — ФИО в таблице сегментов — ссылка
`clients.html?client=N` БЕЗ параметра источника; `clients.js:381–397` —
диплинк открывает карточку, back-механизма нет; эталонный механизм уже есть —
карточка заказа: `admin.html?order=N&back=client:M` + кнопка «← К клиенту»
(`admin.js:2192–2195`, `clients.js:369–374`); возврат в «Статистику»
технически готов — хэш-диплинк `admin.js:2143–2145` (`#stats-clients` →
`switchStatsTab('clients')`).
Решение: отслеживание источника — `clients.html?client=N&back=stats`;
в карточке при `back=stats` — кнопка «← К статистике» →
`admin.html#stats-clients` (ответ на вопрос записки «возможен ли возврат
просто на ту же страницу Статистики по кнопке» — да, существующим
хэш-диплинком; промежуточное модальное окно не требуется). Рекомендация для
черновика волны: параметр `back=` — общий реестр источников (stats, orders),
без дублирования кода карточки заказа. Категория UX · S · **ВОЛНА23**.

**П2. Пользователи → Клиенты: перестройка карточки клиента.**
Код: `clients.html:85–141` — модалка `width:min(720px,100%)`; состав сверху
вниз: заголовок, строка агрегатов (`clm-stats`), блок «История заказов»
(`clm-orders`), «Варианты имён» (`clm-names`), «История контактов»
(`clm-contacts`), затем форма (ФИО/телефон/e-mail/комментарий) и «Сохранить»;
список заказов — flex-строки (`clients.js:202–230 renderOrdersBlock`), кнопка
«№ N» без `white-space:nowrap` — номер переносится на две строки.
Решение (дословно по записке): (а) верх модалки — ФИО, контакты, комментарий
(+ «Сохранить»); (б) ниже — ДВА раскрывающихся блока: ① варианты имён +
история контактов, ② история заказов (паттерн раскрывающихся секций —
`sitecontent.js sc-group`); (в) модалка шире (~min(980px,100%) — уточнение
Д# черновика); (г) список заказов — таблица с min/max-шириной столбцов,
«№ заказа» — nowrap. Категория UX · M · **ВОЛНА23**.

**П3. Статистика → Списания: расположение блоков.**
Код: `admin.html:322–375` — текущий порядок: `wo-kpi` (5 счётчиков —
`admin.js:1687–1692`: строки, сумма списаний, излишки, сумма излишков,
среднее расхождение) → [Причины списаний | Топ списываемых товаров] →
[Администраторы | Проведённые инвентаризации] → [Топ товаров с излишком |
Проведённые ручные списания].
Решение (дословно по записке): верх — те же 5 счётчиков; далее строками:
[Топ списываемых товаров (слева) | Причины списаний (справа)] → [Топ товаров
с излишком (слева) | Администраторы (справа)] → [Проведённые ручные списания
(слева) | Проведённые инвентаризации (справа)]. Перестановка `chart-box`
в разметке; рендеры `admin.js` не меняются. Категория UX · S · **ВОЛНА23**.

**П4. Магазин → Товары: «Полный предпросмотр» загружается нестабильно.**
Код: `products.html:358–362` — ЕДИНСТВЕННЫЙ iframe `#pvfull-frame`
(`sandbox=""`); `products.js:254–297 showPvFrame` — `srcdoc` переприсваивается
при каждом открытии (строка 289), backdrop открывается синхронно; два входа —
`openFullPreview` (298, из карточки товара) и `openDbPreview` (330, «Просмотр»
из таблицы — П14 v0.22.0).
Диагноз (гипотеза — проверить смоуком волны): симптом «первый заход грузится,
несколько карточек подряд — пустой прямоугольник в цвет темы» указывает на
гонку навигаций `srcdoc`: повторное присвоение, пока предыдущий документ ещё
грузит `styles.css`/`fonts.css` (десятки КБ), — навигация теряется, iframe
остаётся пустым; «прямоугольник в цвет темы» — body с инлайн-токенами
(`pvTokenCss`) без контента. Решение (по записке — «стабильность
приоритетнее отсутствия дубля в коде», дублирование кода витрины допустимо):
пересоздание узла iframe при каждом открытии (remove → append нового с
`sandbox=""` → srcdoc), опционально — guard `onload`/однократный retry;
ручной сценарий приёмки — «5 карточек подряд» (§4 п.4 инструкции волны).
Категория Б · M · **ВОЛНА23**.

**П5. Карточка клиента: «не все варианты имени попадают в список».**
Диагностика (живая база, REST 02.11.2026, только чтение): клиент №1 «Мария» —
11 заказов с РАЗНЫМИ именами (Мария ×5, Заказчик, Мэм, Анна, Олег, Узбе,
Людмила, Игорь — заказы #1–#18 от 19.09–05.10.2026), в `client_name_history`
— 2 записи: «Игорь» (source=backfill) и «Мария» (source=admin, 08.10.2026).
Причина: перечисленные заказы созданы ДО применения на живой базе скрипта 28
и `create_order` v9 (09.10.2026); одноразовый backfill (скрипт 28 §5, guard
«таблицы пусты») пишет ОДНУ строку — текущее имя клиента на момент применения,
историю заказов не разворачивает. Начиная с v9 имя пишется в историю КАЖДЫМ
заказом безусловно (`03_functions.sql:381–382`) — подтверждено живой базой:
заказы #19 (17.10.2026, клиент 7 «Мария») и #20 (27.10.2026, клиент 8 «Мария
Панова») — записи source=order на месте. **Вывод: не баг** — расхождение
касается только заказов, оформленных до 09.10.2026.
Решение: (а) фиксация объяснения — этот пункт (ДОК); (б) опция —
дополнительный одноразовый backfill вариантов имён из старых заказов
(`insert … select distinct o.customer_name …` c guard) — потребовал бы
скрипта 38; **рекомендация разработчика — НЕ выполнять** (живая база —
тестовые данные; вопрос Д13 черновика); (в) опция UI — примечание в блоке
«Варианты имён»: «История ведётся с v0.18.0 (09.10.2026); по более ранним
заказам — одна backfill-запись» (вопрос Д14 черновика). Категория СВЕРКА ·
S · **ДОК** (опции — Д13/Д14 черновика волны).
