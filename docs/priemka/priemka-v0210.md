## 0. Принципы обработки

Те же, что в `priemka-v014.md` §0 и `priemka-v015.md` §0: каждый пункт —
проблема → состояние кода (файл:строка) → решение → категория → объём →
маршрут.

**Категории:** Б — баг (код работает не так, как задумано); UX — мелкое
улучшение интерфейса; ПЛАН — крупный функционал/решение в план развития;

документов; СВЕРКА — перепроверка/исправление существующего документа.

**Объём:** S — часы, локальная правка JS/CSS/текста; M — до рабочего дня,

## 1. Постатейная обработка (26 пунктов записок 18.10.2026)

**П1. Форма создания заказа — ссылки ПДн/оферты в текст чек-бокса.**
Код: `index.html:275–277` — текст согласия (`data-content=checkout.consent.text`
из site_content) и отдельный блок `.consent-links` под чек-боксом.
Решение: ссылки «Политика обработки ПДн» (privacy.html) и «Публичная оферта»
(offer.html) — кликабельный подчёркнутый текст внутри уведомления чек-бокса;
отдельный блок ссылок убрать. Текст — из site_content: JS оборачивает
вхождения «персональных данных» и «оферты» в ссылки; если владелец изменит
текст и вхождений не будет — ссылки остаются отдельной строкой (fallback,
без потери юр-смысла). Категория UX · S · **ВОЛНА22**.

**П2. Несколько промокодов одновременно; категории промокодов.**
Код: `orders.promo_code` — один код на заказ; RPC `check_promo` v2 — проверка
одного кода; карточка промокода (`manage.js`) — без категорий и сочетаемости.
Решение: механика крупная (настройка «с чем можно сочетать» в карточке кода;
категории — приветственные/праздничные/извинительные; ввод нескольких кодов;
хранение — массив или промежуточная таблица «заказы-промокоды»; доработка
функции проверки) — новая карта **fp №29** + **ВОПРОС 8.1** владельцу
(граница — до старта проектирования). Категория ПЛАН+ВОПРОС · L ·
**FP №29, ВОПРОС 8.1 (ВЛ-13)**.

**П3. Пересмотр статусной модели — упрощённая обработка заказов.**

Подтверждён → Сборка → …); экран «Сборка» (`assembly.js`).
Решение: крупное — новая карта **fp №30** (переключатель в админ-панели
«ускоренный вариант» / «полная статусная модель»; автопереход Новый →
Подтверждён после письма клиенту — боевая версия, после M4) + **ВОПРОС 8.2**
владельцу («вариативность способов обработки заказов» — дословное указание
записки). В волне v0.22.0 статусная модель НЕ меняется. Категория
ПЛАН+ВОПРОС · L · **FP №30, ВОПРОС 8.2 (ВЛ-13)**.

**П4. Статистика → Клиенты: переход с ФИО в карточку клиента.**

Решение: ФИО — ссылка `clients.html?client=<id>` (переиспользование

**П6. Сегменты «повторные» и «VIP» не пересекаются.**

с выпадающим списком с множественным выбором»): инкремент **скрипт 35** —
`draft_clients_bundle` v4 — независимые флаги `is_new` / `is_repeat` /
`is_vip` (+ прежний `is_dormant`); поле `segment` сохраняется для
совместимости и CSV-выгрузки. Фронтенд: табы → фильтр «Сегмент» с выпадающим

**П8. Статистика → Возвраты: сумма 0 ₽ при возвращённых деньгах; счётчики.**
Код: `admin.js` `returnAggregates` — «Сумма возвратов» считается только по

деньги возвращены, статус не завершён) в сумму не попала — отсюда 0 ₽.
Боксы: `admin.js:1386–1392`.
Решение (дословно по записке): объединить счётчики «оформлено / отклонено»

счётчик денег для ВСЕХ заявок, в том числе незавершённых. Состав боксов:
**Всего заявок · Оформлено / отклонено · Сумма возвратов (заявки с отметкой
«деньги возвращены» — независимо от статуса; исправление 0 ₽) · Сумма заявок
(все, в том числе незавершённые) · Средний срок**. Категория Б+UX · S ·
**ВОЛНА22**.
