## 0. Принципы обработки

«проблема → текущее состояние в коде → решение».

### П3. Цена вариантов товара (L · v1.0, волна M1)
**Проблема:** цена хранится только на товаре: `products.price`
(01_schema.sql:46), у `product_variants` колонок цены нет — только `label`,
`stock`, `sort_order` (01_schema.sql, таблица `product_variants`). Для одежды
это терпимо (S/M/L одна цена), для парфюмерии неверно по сути: 30/50/100 мл —
разные цены. Сейчас объёмы флаконов различаются только остатком.
**Что делать:** колонка `product_variants.price_override numeric(10,2) null`
(null = наследовать цену товара) либо полный перенос цены на вариант с
`products.base_price` как витринной «от …». Затрагивает: карточку товара
(цена меняется при выборе варианта), корзину и снапшот `order_items.price`
(уже снапшотируется — ок), скидку комплектов (`lookSum` в site.js:290 —
считает от `p.price`), серверный пересчёт заказа (`draft_place_order`),
CSV-посев каталога (скрипт 05 — цены в колонке товара), статистики не
затрагивает (считают от снапшотов).
**Рекомендация:** делать в M1 до боевого наполнения каталога — миграция цен
по существующим заказам болезненна, а парфюмерия — половина ассортимента.

### П6. Персонализация карточки товара для категорий (L · v1.x, feature-proposals №14)
**Проблема/идея (дословно по запискам):** «на карточке категории создаются
дополнительные поля, которые позже заполняются в карточке товара. Пример:
стойкость аромата у парфюмерии». Сейчас у категорий только `name`, `slug`,
`description` (01_schema.sql:38); характеристики товаров едины для всех
категорий — «стойкость», «объём», «состав», «сезон» некуда записать.
**Что делать (EAV-схема, черновик):** `category_attrs` (category_id, code,
label, type: text/number/enum, enum_values, sort_order, show_on_card bool) +
`product_attrs` (product_id, attr_id, value). В админке: у категории —
конструктор атрибутов; в карточке товара — динамическая секция по категории.
На витрине: блок характеристик в модалке товара; `show_on_card` — выводить ли
в списке (например, «стойкость» чипом у парфюмерии). Связано с п.27 (описание
категории на витрине не выводится — появится вместе с персонализацией).
**Маршрут:** пользователь явно просила добавить пункт в feature-proposals.md —
будет внесен как предложение №14 в следующую документальную волну.

### П8а. Политика имён клиентов при слиянии + варианты имени (M · CRM, v1.x)
**Проблема:** при каждом новом заказе имя клиента перезаписывается именем
из заказа: upsert в `draft_place_order` — `full_name = excluded.full_name`
(16_race_and_integrity_fixes.sql:367 и ветка 396), миграция script 15 —
`set full_name = o.customer_name` (15_clients_and_promo_stats.sql:156).
Ответ на вопрос записок: **побеждает самое последнее имя** (из свежего заказа),
изменения администратора затираются автоматически. Это же обесценивает
ручную правку ФИО в карточке клиента.
**Что делать:** (1) флаг `clients.name_confirmed boolean` — имя, подтверждённое
админом, upsert не перезаписывает (только до первого подтверждения);
(2) история имён: `client_name_history` (client_id, full_name, source:
order/admin/merge, created_at) или jsonb-массив `name_variants` — в карточке
клиента показывать варианты («Иван П. / I. Petrov / Иван Петров»);
(3) правило слияния дублей (сейчас — вручную в Table Editor по подсказке
clients.js:205) — формализовать: при слиянии имена обоих уходят в историю.
**Решение по умолчанию (если владелец не возразит):** последнее имя — из
заказа, но подтверждённое админом имя не перезаписывается; все прежние
варианты видны в карточке.

## 4. Перепроверки и анализ (без изменения кода в этой работе)

### П39. Комментарий к клиенту «затёрся / не был сохранен» — в коде не воспроизводится
Проверено: поле `note` есть в схеме (15_clients_and_promo_stats.sql:77),
карточка клиента его читает (clients.js:168) и **сохраняет** в payload
`update` (clients.js:196: `note: note || null`); upsert клиента при новом
заказе (16:364-400) колонку `note` **не трогает** — заказ не может затереть
комментарий. Возможные объяснения наблюдаемого:
1. **Подмена карточки:** после смены контактов (п.40) или ручного слияния
   дублей в Table Editor (подсказка clients.js:205) заказ/телефон «переехал»
   на другого клиента — открылась карточка без комментария;
2. **Не сохранено:** правка комментария без нажатия «Сохранить» (модалка
   закрывается кликом по фону — clients.js, backdrop-handler — правки теряются
   молча);
3. Единичный сбой сети (ошибка update показывается, но если карточку закрыли —
   не заметно).
**План перепроверки (в волну):** (а) создать клиента-тест → комментарий →
сохранить → перезагрузить страницу → проверить; (б) новый заказ с тем же
телефоном → проверить, что комментарий на месте; (в) сменить телефон в
карточке → сделать заказ на старый телефон → посмотреть, куда привязалось;
(г) рассмотреть защиту от (2): предупреждение при закрытии модалки с
несохранёнными правками (dirty-check) — мелкая правка, добавить в волну,
если сценарий подтвердится.

### П40. Смена контактных данных клиента — привязка заказов сохраняется
Анализ: заказы привязаны **по id**: `orders.client_id` → `clients.id`
(FK, 15_clients_and_promo_stats.sql:108) — изменение телефона/e-mail в
карточке клиента (clients.js:192-199 пересчитывает `phone_key`/`email_key`)
привязку **не разрывает**. Нюансы:
1. В заказах остаются snapshot-поля `customer_phone`/`customer_email`/
   `customer_address` — история не перезаписывается (это правильно: данные
   на момент заказа); расхождение «контакты клиента ≠ контакты старых
   заказов» — норма, в карточке показывать актуальные из `clients`;
2. Если новый заказ придёт на **старый** телефон, а ключ уже освобождён —
   создастся новый клиент (или смержится по e-mail) — потенциальный дубль;
   защита от коллизий уже есть (unique `phone_key`/`email_key` + обработка
   23505 в clients.js:203-207 с подсказкой слить вручную);
3. При слиянии дублей вручную заказы перепривязываются в Table Editor —
   формализация слияния (с переносом заказов, имён и комментариев) — часть
   П8а (политика имён и слияний).
**Вывод:** менять контакты можно, привязка заказов не теряется; риск —
дубли при заказах на старые контакты, решается формализацией слияния (П8а).

### П27. Где видно описание категории

### П23-уточнение. Доставка в статистике уже учтена
Замечание «оплата доставки тоже должна входить в статистику» фактически
выполнено: все денежные суммы считаются как `total + delivery_cost`
(admin.js:289-291 KPI, 524-526 CSV, 540 по дням, 748-751 промо-сплит);
`orders.delivery_cost` — отдельная колонка (01_schema.sql:123), в таблице
