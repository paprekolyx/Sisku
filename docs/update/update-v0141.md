## 1. Что изменилось

### 1.1. База — V4: повторный прогон скрипта 02 больше не откатывает фикс F09

**Проблема (воспроизведена ревью на живой базе):** скрипт 16 расширял чтение
`payment_methods`/`delivery_methods` для anon до `using (true)` — часть фикса
F09 (отключённый способ должен быть виден в админке, чтобы его можно было
включить обратно или удалить). Скрипт 02 продолжал создавать те же политики
с `using (is_active = true)`. Полный прогон 01→16 сходился корректно, но
**повторный прогон одного 02 после 16 молча откатывал расширение** — нарушен
контракт реестра «скрипты идемпотентны, повторный запуск безопасен».

**Исправление (по рекомендации ревью — истина в одном месте):**

- `supabase/02_rls_and_access.sql` — обе политики `anon_read_payment_methods`
  и `anon_read_delivery_methods` создаются с `using (true)` + комментарий
  (v0.14.0, фикс F09; граница — `create_order()` и витрина используют только
  активные способы, проверяется на сервере). Повторный прогон 02 после 16
  теперь безопасен.
- `supabase/16_race_and_integrity_fixes.sql` — блок 5 оставлен как есть
  (drop/create идемпотентны, сводят состояние старых баз), добавлен
  комментарий, что с v0.14.1 политики чтения создаёт и скрипт 02.
  **Объекты БД не меняются — повторный прогон 16 не требуется.**
- `supabase/README.md` — описание строки 02 и раздела «Решения,
  зафиксированные в скриптах» приведено к новому порядку.

Количество политик не изменилось (58); состав и версии функций — без изменений.

### 1.2. Фронтенд — N1 и N2

- **`assets/js/util.js` (N1):** `safeUrl()` первым делом очищает строку от
  управляющих символов и пробелов (`[\u0000-\u0020]`) и только затем проверяет
  схемы. Раньше `'java\tscript:alert(1)'` не матчил ни whitelist, ни blacklist
  (TAB разрывал паттерн схемы) и возвращался как «относительный путь», а
  браузеры при резолве URL вырезают TAB/LF/CR — в `href` попадал исполняемый
  `javascript:`. Защита defense-in-depth для боевой версии (в черновике
  `site_content` и так редактируется анонимно — границы описаны в SECURITY.md).
- **`assets/js/site.js` (N2):** `revalidatePromo()` вызывается и при
  **добавлении** товара в корзину (`addToCart`, кнопка «В корзину» в карточке)
  и при добавлении комплекта («В корзину целиком»). Ранее фикс F30 покрывал
  только изменения в drawer'е (±/убрать/очистить) — при применённом
  процентном промокоде сумма скидки в сводке устаревала. Комплект
  перевалидируется одним вызовом (позиции добавляются с флагом `skipPromo`) —
  без лишних RPC на бесплатном тарифе. Без промокода вызов ничего не делает;
  деньги по-прежнему считает только сервер (`create_order`).

## 4. База, публикация и проверка

1. **Supabase SQL Editor:** новых скриптов нет. Скрипт 16 выполнен в волну
   v0.14.0 — база уже в целевом состоянии, **обязательных действий нет**.

   `supabase/02_rls_and_access.sql` целиком, затем:
   ```sql
   select policyname, qual from pg_policies
   where tablename in ('payment_methods','delivery_methods')
     and policyname like 'anon_read%' order by policyname;
   ```

   больше не откатывает. Для восстановления базы с нуля — как раньше,

2. Загрузить файлы раздела 2 в репозиторий, в config.js править только
   SITE_VERSION. Push в `main` → Pages → на сайте **Ctrl + F5**.
3. **Чек-лист приёмки:**
   - сайт открывается; в подвале и на `login.html` версия **0.14.1-draft**;
   - «Управление → Оплата и доставка»: отключённый способ виден в списке,
     включается обратно и удаляется (если не использован в заказах) — после

## 7. Урок для регламента (SQL)

**Расширение, внесённое поздним скриптом, обязательно дублировать в
скрипте-источнике объекта.** Повторный прогон любого скрипта цепочки не
должен откатывать итоговое состояние базы (контракт «идемпотентность =
безопасность повторного запуска»). Практическое правило волны: правка
политики/функции в скрипте N проверяется сценарием «прогнать 01…N, затем
повторно каждый скрипт 01…N−1 по одному и сверить состояние» — минимум для
объектов, которые трогают несколько скриптов (политики чтения справочников
02↔16, create_order 03↔15↔16).
