## 1. Что изменилось

### 1.1. База — четыре новых скрипта (22–25)

| Скрипт | Что делает |
|---|---|
| `22_return_reasons_and_requests.sql` | Справочник `return_reasons` (id, name, is_active, **sort_order** — имя колонки по конвенции проекта) + сид 4 причины («Не подошёл размер», «Брак / дефект», «Не подошло», «Передумал(а)» — только если справочник пуст). Таблица `return_requests`: заказ, причина, комментарий, `photo_urls` jsonb (**заглушка до хранилища M5**), статус `created → returned_to_stock → verified / rejected` (CHECK), блок «деньги возвращены» (`refund_paid`/`refund_paid_at`/`refund_receipt` — в макете необязательные), `created_by`/`handled_by` — **текст** (паттерн `order_status_history.changed_by`; FK на пользователей — в боевой M2), `created_at`/`resolved_at`; индексы по заказу и статусу. RLS: чтение причин публично, запись причин — draft-политики insert/update **без DELETE** (удаление — только деактивацией); чтение заявок — draft (как заказы); **запись заявок — только через RPC** (прямых политик нет — самопроверка скрипта это контролирует). RPC: `create_return_request(p jsonb)` — заявка покупателем (заказ существует, статус **shipped/delivered**, код подтверждения — механизм `track_order`, причина активная, комментарий ≤ 2000, антиспам: одна незакрытая заявка на заказ + ≤3 заявок/10 мин); `admin_set_return_status(...)` — переходы по модели заявки, при «Товар вернулся на склад» заказ **автоматически переводится в «Возврат»** (через `admin_set_status`; идемпотентно — если заказ уже «Возврат», «без изменения»), финальным статусам пишется `resolved_at`; `admin_set_return_refund(...)` — флаг + дата + реквизиты чека; `draft_returns_bundle()` — очередь одним RPC (заявки + причины + тексты `returns.*`; заказы/статусы — из `draft_admin_bundle`). `track_order` **v2** — +`status_code`/`status_name`/`return_available` (состав v1 сохранён). `draft_storefront_bundle` **v2** — +`return_reasons` (активные). Модель переходов заказов **+ `shipped → returned`** (возврат до простановки «Доставлен») |
| `23_quarantine.sql` | Карантин F51 — **схема (а) счётчик** (утверждена 06.10.2026): `product_variants.quarantine_qty` (CHECK ≥ 0) + `admin_set_status` **v4**: «Отменён» — остатки в `stock` (как раньше), «Возврат» — **в карантин** (в продажу не возвращаются); обратный переход из «Возврата» моделью не разрешён (returned — финальный). RPC осмотра `admin_resolve_quarantine(variant_id, qty, action, changed_by)`: `restock` — вернуть в продажу (карантин → stock), `writeoff` — списать; `FOR UPDATE` на варианте, `qty ≤ quarantine_qty`. `draft_assembly_bundle` **v2** — остатки склада с `quarantine_qty`. Складские движения (журнал, партии) — fp №3b (v0.28.0) |
| `24_return_content_keys.sql` | **18 ключей** `site_content` `returns.*` (52 → **70**): форма возврата витрины (заголовок, подсказка, подписи полей и плейсхолдеры, фото-заглушка, кнопка, текст принятия), кнопка «Оформить возврат» в окне отслеживания, подписи статусов очереди админки, название раздела статистики. Формулировки **нейтральные — до юрблока M4** (ЮР-03/ЮР-06). Вставки только «где ключа ещё нет» (культура F21) |
| `25_delivery_seed_align.sql` | ⚠ **Одноразовая миграция данных с guard** (АН-20): выравнивание НОВЫХ баз с живым состоянием (бэкап 06.10.2026) — `delivery_methods`: `boxberry` → код `pochtaruss`, имя «Почта России, 3–8 дней» (цены не трогаются — вилка 300–800 ₽ совпадает); `site_content`: «Boxberry» → «Почта России» в `order.delivery.text`/`adv.3.text`/`checkout.hint.address`. Guard — WHERE по старому значению: **на живой базе — no-op** (владелец уже исправил), повторный прогон безопасен, но по регламенту — один раз |

Все скрипты — по регламенту 8 правил (`supabase/README.md`): идемпотентность
(кроме data-части 25 — guard), префлайт `to_regclass`, парные `$$`,
`policyname`, шапка + самопроверка с точными ожидаемыми значениями, агрегаты
не вложенные. Проверено: pglast + прогон на живом PostgreSQL 15
(цепочка 01→25 на свежей базе, двойной прогон 22–25, смоук-тесты RPC —
полная цепочка «заказ → доставка → заявка → статусы → карантин → осмотр →
продажа», регресс отмены, RLS под ролью anon: чтение открыто, прямая запись
заявок запрещена, удаление причин запрещено).

### 1.2. Витрина (index.html, site.js, styles.css)

- **Форма «Оформить возврат»** (модалка `return-modal-backdrop`): номер
  заказа и код подтверждения — подставляются из окна отслеживания
  (readonly), причина — select из справочника (только активные), комментарий,

  `friendlyDbError`); успех — экран с номером заявки.

  возврат» показывается только при `return_available` из `track_order` v2 —
  статусы **«Отправлен» и «Доставлен»** (решение 06.10.2026); из «Возврата»
  повторные заявки не создаются (серверный антиспам — одна незакрытая
  заявка). Тексты формы — из ключей скрипта 24 (`data-content`).

  (названия — только из справочника `delivery_methods` и `site_content`).
- **Правка 2.1 (З1-баг):** товар без вариантов (или без наличия по всем
  вариантам) — в модалке «нет в наличии» (вместо «варианты не заданы»),
  кнопка «В корзину» неактивна; тост «Выберите размер» — только когда
  варианты в наличии реально есть; иначе — «Товара нет в наличии».
- **Правка 2.2 (З2):** в комплекте единственный вариант товара — выбран по
  умолчанию (без «Выберите размер…»; единственный вариант без наличия —

  (`body.overflow hidden` при открытии; восстановление при закрытии — только

## 7. Урок для регламента

**Грабля №15 (новая, найдена в этой волне; реестр граблей — заметки аналитика §4): pglast НЕ проверяет тела
функций `language sql`.** `create or replace function … language sql
as $$ … $$` для внешнего парсера — строковый литерал: лишняя закрывающая
скобка внутри `jsonb_build_object` прошла pglast, но упала на первом же
прогоне в PostgreSQL («syntax error at or near )»). Вывод: прогон на живом
PostgreSQL (или хотя бы `check_function_bodies` + создание функции на
тестовой базе) обязателен для каждого нового скрипта — pglast ловит только
ошибки верхнего уровня. Уже входит в регламент (§5 «проверка — pglast +
прогон»), зафиксировано как напоминание: **прогон — не формальность**.
