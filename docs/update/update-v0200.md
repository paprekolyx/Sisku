## 1. Что изменилось (состав волны)

### 1.0. Решения до старта волны (ответы аналитика 10.10.2026)

**Д1** — состав БД: 4 таблицы (`writeoff_reasons`, `inventory_sessions`,
`inventory_items`, `writeoffs`); таблицы **24 → 28**. **Д2** — статусы
`planned → in_progress → done` + **`cancelled`** (отмена из любого статуса,
кроме `done`; переходы — **только ручные**, авто-старта по план-дате нет;
сессия без расхождений завершается нулевой; **параллельные идущие сессии
разрешены** — ответ 7.3(а), guard «одна идущая» НЕ делается). **Д3** — область
`all`/`categories` + `scope_categories` jsonb; участники — id из `admin_users`
(отображение ФИО; авторство текстовое до M2); план-дата nullable. **Д4** —
колонки листа: товар · вариант · остаток в системе · в резерве · в карантине ·
**ожидаемо физически** (= сумма трёх — всё физически на складе) · факт (ввод) ·
**расхождение со знаками «+» (излишек) / «−» (недостача)** и подсветкой;
сохранение факта — batch одним RPC. **Д5 (АН-21, вариант (б))** — завершение
одной транзакцией: по каждому ненулевому расхождению строка журнала + `stock
+= diff` **без запрета минуса**; **предупреждение — модалка фронтенда перед
проведением** (перечень расхождений + ожидаемые новые остатки + текст про
ноль/минус и резервы); **CHECK `stock >= 0` у `product_variants` снят
скриптом 31**; защиты: витрина — условное списание `create_order` (v9, не
меняется), сборка — минус/ноль виден и подсвечен; завершение — только роль
«администратор» (7.3(б); до M2 — мок-гейт); guard ручных списаний `stock + qty
>= 0` **сохранён** (минус — только через проведение). **Д6** — причины
завершения: недостача → `shortage`, излишек → `surplus` (системные, не
деактивируются); комментарий строки — «Инвентаризация № X». **Д7** — ручные
списания вне инвентаризации — да, кнопкой в журнале панели (карточка товара
не раздувается). **Д8** — подвкладка «Статистика → Списания» (паттерн
«Возвратов»: ленивый бандл, свой период): KPI, топ товаров, причины
(по умолчанию таблица), админы, разрез проведённых инвентаризаций, CSV; суммы
— **по текущей цене товара** (в бою — закупочная и цена продажи на момент
инвентаризации — **fp №28**, зарегистрирован 10.10.2026). **Д9** — два бандла
(грабля №6). **Д10** — RLS: справочник причин — anon-чтение + draft-insert/
update (+3 политики, **62 → 65**; удаление — только деактивацией); сессии/
лист/журнал — RLS без анонимных политик (запись — RPC, чтение — бандлы;
паттерн истории клиента v0.18.0). **Д11** — посев **5 причин БЕЗ «Уценки»**
(ответ 7.2: уценка — вид акции): Брак, Витринный образец, Недостача
(системная), Излишек (системная), Прочее; управление — **«Управление →
Справочники»**. **Д12** — панель из трёх секций (планирование / лист /

### 1.1. База — скрипты 31 и 32

- **`supabase/31_inventory_schema.sql` (НОВЫЙ):** 4 таблицы + индексы +
  комментарии; **снятие CHECK `product_variants_stock_check`** (Д5, вариант
  (б); минус/ноль — допустимое состояние после проведения, комментарий
  колонки `stock`); посев справочника — **5 причин без «Уценки»** (on conflict
  do nothing — F21); RLS: 4 таблицы enable, `writeoff_reasons` — 3 анонимные
  политики (read/insert/update — паттерн `return_reasons`, delete отсутствует),
  остальные — без анонимных политик; префлайт; самопроверка — строка
  `t|t|t|t|65|t` (таблицы 4, RLS 4, посев 5, системных 2, **политик 65**,
  CHECK снят).
- **`supabase/32_inventory_rpc.sql` (НОВЫЙ):** 6 RPC записи + 2 бандла
  (LANGUAGE sql, SECURITY DEFINER): `admin_create_inventory_session(p)` —
  валидация (область, категории, участники, план-дата) → 'planned' + лист
  snapshot'ом одной вставкой (активные варианты области; резерв — открытые
  статусы new/confirmed/packing, механизм `draft_reserved_map` v2; карантин —
  `quarantine_qty`); `admin_start_inventory_session` — 'planned' →
  'in_progress' + **пересчёт snapshot** (без guard «одна идущая» — 7.3(а));
  `admin_cancel_inventory_session` — из 'planned'/'in_progress' (из 'done' —
  ошибка; факты сохраняются, списания не проводятся);
  `admin_save_inventory_items(p)` — batch-факты одной транзакцией (сессия
  должна идти; fact_qty целое 0–99999; diff пересчитывает сервер);
  `admin_finish_inventory_session` — проведение (Д5/Д6): FOR UPDATE в
  детерминированном порядке variant_id (F23), журнал + `stock += diff` без
  guard на минус, сводка в ответе (`writeoffs_created`, `shortages`,
  `surpluses`, `negative_positions` — для протокола); повторное завершение и
  завершение отменённой — ошибки; `admin_create_writeoff(p)` — ручное
  списание/излишек (qty ≠ 0, причина активна, **guard `stock + qty >= 0`
  сохранён**, комментарий ≤ 1000); `draft_inventory_bundle(p_session_id)` —
  без id: сессии (агрегаты листа, ФИО участников, имена категорий) + причины +
  категории + активные админы; с id: + лист (snapshot/факт/расхождение/
  `stock_now`); `draft_writeoffs_bundle()` — журнал (товар/вариант/артикул/
  **текущая цена** для сумм, qty ±, причина, автор, комментарий, session_id) +
  причины + проведённые сессии с итогами. **`create_order` не меняется (v9).**
  Самопроверка — строка `t|t|t|t|t|t|t|t|t|28` (8 функций, create_order v9,
  **функций 28**).
- Счётчики: таблицы **24 → 28**, политики **62 → 65**, функции **20 → 28**,
  скрипты **11 → 13** (baseline 6 + инкременты 26–32), следующий — **33**;
  ключи `site_content` — **73 (без изменений)**.
- Бэкапы `data/`: сессии/лист/журнал — производные операционных данных, **не
  выгружаются** (как заказы/клиенты); справочник причин — **новый бэкап
  `data/writeoff_reasons_rows.csv`** (5 строк — посев; Д13: в REQUIRED не

- Живая база: только инкременты 31 → 32 (модель F21); идемпотентны

### 1.2. Админка — панель «Магазин → Инвентаризация» (products.html + inventory.js)

- Заглушка v0.15.0 заменена рабочей панелью из трёх секций (Д12), модуль —
  **`assets/js/inventory.js` (НОВЫЙ, Д14)**; подключение — в products.html
  после products.js; данные — два бандла (лениво при каждом открытии панели);
  переключение панелей по hash — без изменений (products.js).
- **«Планирование»:** таблица сессий (№, область, план-дата, статус-пилюля
  (planned/in_progress/done/cancelled), позиций/посчитано + отметка «± N»
  расхождений, участники (ФИО), создана, действия); «Новая инвентаризация» —
  модалка (область всё/категории + мультивыбор категорий, план-дата —
  датапикер ui.js, участники — мультивыбор админов); действия: «Начать»
  (planned), «Открыть лист» (in_progress), «Отменить» (planned/in_progress —
  модалка подтверждения; из done недоступно), «Итоги» (done).
- **«Лист»:** колонки Д4 (в системе / в резерве / в карантине / ожидаемо
  физически / факт / расхождение), sticky-заголовок; расхождение считается
  на лету, знаки **«+» (излишек) / «−» (недостача)** и подсветка строк
  (минус — danger-фон 8%, плюс — ok-фон 8%); «Сохранить факт» — batch одним
  RPC (блокировка повторной отправки); «Завершить» — **модалка предупреждения
  (Д5)**: перечень расхождений (позиция, ожидаемо, факт, ± qty, ожидаемый
  новый остаток; уход в ноль/минус помечается) + текст «остатки могут стать
  нулевыми или отрицательными; единицы зарезервированы под открытые заказы —
  проверьте сборку» → «Провести» → сводка проведения (строк журнала, списано/
  излишки шт., позиции с нулём/минусом); для done/cancelled — лист только
  для просмотра с соответствующей подсказкой; подсказка про snapshot старта
  (продажи во время сессии лист не меняют).
- **«Журнал списаний»:** фильтры (причина / сессия (включая «Ручные (вне
  сессий)») / поиск товара), пагинация 30; строки: дата, товар (артикул),
  вариант, qty ± (цвет), причина, автор, комментарий, сессия-кнопка (открывает
  итоги); «Ручное списание» — модалка (поиск варианта по товару/артикулу/
  размеру со свободным остатком, qty «−»/«+», причина (активные), комментарий;
  серверные guard'ы — свободные единицы, ≠ 0); CSV журнала (BOM, «;»,
  анти-формульная защита F06, локальная дата в имени F29).

## Приложение Б. Формы RPC (фактические)

    admin_create_inventory_session(p) : p = { scope: 'all'|'categories',
      category_ids?: [int], plan_date?: 'YYYY-MM-DD', participant_ids?: [int],
      created_by? } → { ok, session_id, items_count }
    admin_start_inventory_session(p_session_id, p_changed_by) → { ok }
    admin_cancel_inventory_session(p_session_id, p_changed_by) → { ok }
      | raise: «Завершённую сессию нельзя отменить»
    admin_save_inventory_items(p) : p = { session_id, changed_by?,
      items: [ { item_id, fact_qty } … ] } → { ok, saved }
    admin_finish_inventory_session(p_session_id, p_changed_by)
      → { ok, writeoffs_created, shortages, surpluses, negative_positions }
      (вариант (б): без raise на минус; negative_positions — [{variant_id,
      product, variant, stock}] — для протокола; предупреждение — модалка
      фронтенда до вызова)
    admin_create_writeoff(p) : p = { variant_id, qty (≠0, |qty| ≤ 99999),
      reason_id (активная), comment? ≤1000, changed_by? } → { ok, writeoff_id }
    draft_inventory_bundle(p_session_id default null) →
      { sessions[] (id, scope, scope_categories, scope_names, plan_date,
        status, participants, participant_names, created_by, started_at,
        finished_at, created_at, items_total, items_counted, discrepancies),
        reasons[], categories[], admins[] (активные),
        sheet?: [ { item_id, variant_id, product_id, article, product,
                    variant, system_qty, reserved_qty, quarantine_qty,
                    expected_qty, fact_qty, diff, stock_now, counted_by,
                    updated_at } … ] }
    draft_writeoffs_bundle() →
      { writeoffs[] (id, created_at, variant_id, product_id, article, product,
        variant, price — текущая, qty, reason_id, reason, reason_code,
        session_id, comment, changed_by),
        reasons[],
        sessions[] (проведённые: id, scope, plan_date, created_at, started_at,
        finished_at, writeoff_lines, writeoff_qty, surplus_lines, surplus_qty) }
