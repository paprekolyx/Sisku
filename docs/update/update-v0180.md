## 1. Что изменилось (состав волны)

### 1.0. Решения до старта волны (утверждены аналитиком 09.10.2026)

**Д1** — модель данных: колоночная (`clients.phone/email/phone_key/email_key`)
+ две таблицы истории; отдельная таблица `client_contacts` НЕ создаётся
(правило «заказ на старые контакты → новый клиент» работает автоматически:
старые ключи перестают совпадать). **Д2** — вариант (а): смешанный случай
«старый телефон + текущий e-mail» → слияние по e-mail (согласованный ключ
владельца) + фиксация телефона в истории («предложен в заказе»). **Д3** —
`create_order` v9: пары (phone, phone_key) и (email, email_key) при слияниях
не перезаписываются — устранено рассогласование v8 (`email` обновлялся,
`email_key` — нет). **Д4** — сохранение карточки: RPC `admin_update_client`,
одна транзакция. **Д5** — данные карточки: один RPC
`draft_client_card_bundle` на открытие (без N+1 — грабля №6). **Д6** —
переход к заказу: диплинки `clients.html?client=N` и
`admin.html?order=N&back=client:M` (обобщение механизма «← К заявке»
v0.16.0). **Д7** — отображение ФИО: без изменения кода — главное, чтобы
показывалось подтверждённое имя (семантика v7+ уже обеспечивает приоритет
«подтверждённое → последнее → первое»). **Д8** — в пакет включены чистые
копии всех 17 HTML (ведущие пустые строки — артефакты Web-UI-загрузок, к
v0.17.1 на всех страницах; сверка 09.10.2026, находка 1) + обязательная
проверка первых байтов после загрузки. **Д9** — содержимое папок `.jpg/`
оставлено без изменений (решение аналитика; оценка формата содержимого
разработчиком зафиксирована в отчёте сверки 09.10.2026). **Д10** —
check-repo v2.7.

### 1.1. База — скрипты 28–29, `create_order` v9

- **`supabase/28_client_history.sql` (НОВЫЙ):** таблицы
  `client_name_history` (client_id, full_name, source: order/admin/merge/
  backfill, created_by, created_at) и `client_contact_history` (client_id,
  type: phone/email, value, action: set/changed/offered/invalidated,
  changed_by, created_at) + индексы (client_id, created_at) + комментарии;
  RLS включён, **анонимных политик нет** — доступ только через SECURITY
  DEFINER RPC скрипта 29 (счётчик политик не меняется — 62);
  ⚠ **одноразовый backfill** существующих клиентов с guard (пустые таблицы;
  phone+email — один запрос, повторный прогон — no-op).
- **`supabase/29_client_card_v9.sql` (НОВЫЙ):**
  - `create_order` **v9** (база — v8, скрипт 26; вся логика v8 сохранена,
    кроме оговорённой): (1) каждый вариант имени из заказа — в
    `client_name_history` ('order'); перезапись `full_name` — только при
    `name_confirmed = false` (логика v7/правки 2.20); (2) слияние — только
    по e-mail (exception-ветка v8 сохранена; телефон при слиянии
    принимается, только если у клиента его нет и ключ свободен — сырая
    23505 исключена); (3) Д3: при конфликте phone_key пары (email,
    email_key) не изменяются; отличный от текущего контакт заказа —
    'offered' в историю; (4) заказ на контакты, которых нет ни у одного
    клиента (в т.ч. изменённые админом старые) — INSERT нового клиента +
    'set' в историю; (5) мёртвый exception-блок email-ветки v8 убран
    (в ней `v_pkey` заведомо null). Функция собрана программным патчем
    текста v8 из скрипта 26 (`workaichat/pgtest/build_v0180.py`, каждая
    замена — с контролем единственности): неизменяемые части —
    байт-в-байт.
  - RPC **`admin_update_client(p jsonb)`** (Д4): валидация (ФИО обязательно
    и ≤1000; хотя бы один контакт; телефон — 11 цифр с ведущей 7 после
    нормализации; e-mail — маска; комментарий ≤2000) → `FOR UPDATE` строки
    клиента → update `clients` (включая пересчёт ключей и
    `name_confirmed = true` — правка 2.20 сохранена) → история: старый
    контакт 'invalidated' + новый 'changed' (admin), смена ФИО — 'admin'
    в историю имён; 23505 → читаемое сообщение. Одна транзакция (прецедент —
    `draft_save_look`, v0.15.0).
  - RPC **`draft_client_card_bundle(p_client_id integer)`** (Д5): одним
    jsonb — клиент, варианты имён (asc), история контактов (asc), все
    заказы (desc) с позициями (снапшоты), статусами (code+name) и
    `is_paid`; форма — приложение Б.
- Счётчики: таблицы **22 → 24**, функции **18 → 20**, политики — 62 (без
  изменений), скрипты **8 → 10**, следующий — **30**.
- Живая база: baseline НЕ перезапускать (модель F21) — выполнить **28**,
  затем **29**; самопроверки: 28 → `t|t|t|t|t|t`, 29 → `t|t|t|t|t|t|20`.

### 1.2. Админка — clients.html / clients.js / admin.js

- **Карточка клиента** (модалка `cl-modal`): новые блоки — «История
  заказов» (№-кнопка, дата, пилюля статуса, сумма total+delivery с отметкой
  «оплачен», состав второй строкой; пусто — «Заказов пока нет»), «Варианты
  имён» (новые сверху; бейдж «подтверждено» при `name_confirmed`; текущее
  имя выделено), «История контактов» (тип, значение, действие: указан /
  изменён / предложен в заказе / утратил силу, автор, дата); плашка ошибки
  загрузки истории — отдельно от ошибки формы.
- **Клик по № заказа** → `admin.html?order=N&back=client:M` (Д6);
  **admin.js:** `openOrder(id, back)` обобщён — back = { kind: 'return' |
  'client', id }; в шапке карточки — «← К заявке на возврат № X» (как
  v0.16.0) или «← К карточке клиента» (→ `clients.html?client=M`);
  повторное открытие карточки после смены статуса/оплаты сохраняет контекст
  (`state.orderBack`); обработка `?order=N&back=client:M` — строго после
  загрузки бандла (гонка исключена), заказ не найден — плашка;
  `admin.html` — без правок разметки.
- **Сохранение карточки** — `db.rpc('admin_update_client', { p: {...} })`
  вместо прямого `.update()`; клиентская валидация сохранена (быстрый
  отклик), серверная — истина; после успеха — список и карточка
  перезагружаются, модалка остаётся открытой.
- **Диплинк `clients.html?client=N`** — карточка открывается после
  `load()`; клиент не найден — плашка «ссылка устарела».
- **Список клиентов:** отметка подтверждённого имени (✓ за ФИО с
  подсказкой); поиск/сортировка/пагинация 30/маскирование/«глазик»/CSV —
  без изменений (v0.13.0/v0.14.0).
- **Витрина — без изменений** (заказ покупателя пишет историю через v9
  автоматически).
