**Куда смотреть:** этот файл — порядок применения обновления v0.13.1 → v0.14.0
(MINOR-волна: устранение находок независимого ревью — гонки и целостность БД,
экранирование/CSV, фронтовые баг-фиксы, честность документации).

**Основание:** `docs/review-v0131.md` — отчёт независимого ИИ-ревьюера
(ревизия 2, 04.10.2026), находки F01–F52 с решениями аналитика. Волна
выполнена по приложению В отчёта. **F21 (guard повторного прогона data-миграций
06–08) в волну НЕ вошёл — решение аналитика ещё ожидается**; текущее поведение
описано честно в SECURITY.md §4 и docs/setup-supabase.md.

## 1. Что изменилось

### 1.1. База — новый скрипт `supabase/16_race_and_integrity_fixes.sql`

Ревью воспроизвело на живом PostgreSQL 15 **три настоящие гонки** и дефекты
целостности; всё закрыто одним скриптом (по регламенту: префлайт, идемпотентность,
самопроверка):

| Фикс | Что было | Что стало |
|---|---|---|
| F01 · `admin_set_status` v3 | две параллельные отмены возвращали остатки на склад **дважды** + дубль в истории | строка заказа блокируется `SELECT … FOR UPDATE`; второй вызов видит новый статус и возвращает «без изменения» |
| F02 · клиент в `create_order` v6 | два параллельных заказа одного нового клиента → сырая ошибка 23505, заказ потерян | UPSERT `ON CONFLICT (phone_key/email_key) DO UPDATE`; оба заказа пишутся, клиент один |
| F03 · лимит промокода | `usage_limit=1` пробивался двумя параллельными заказами (`used_count=2`) | строка кода блокируется, лимит перепроверяется под блокировкой, инкремент условный |
| F07 · отрицательный итог | fixed-промо + скидка комплекта давали `total = −19560 ₽` | `greatest(total, 0)` + констрейнт `orders_total_nonneg CHECK (total >= 0)`; найденные отрицательные итоги обнуляются (DANGER-блок, тестовые данные) |
| F08 · дубль варианта в корзине | две строки одного варианта проходили валидацию порознь → сырое 23514 наружу | корзина нормализуется (qty суммируется), списание условное `WHERE stock >= qty` с читаемым сообщением |
| F12 · join позиций | в v5 потерялось условие `vr.product_id = pr.id` (мина под будущие правки) | условие возвращено |
| F17 · анти-спам | «+7 999…» и «8999…» считались разными людьми | сравнение по `draft_phone_key()` |
| F18 · `draft_reserved_map` v2 | в открытых статусах остался мёртвый `'paid'` | список: new/confirmed/packing |
| F23 · deadlock | порядок блокировок задавал клиентский массив | детерминированная сортировка: товары по id, затем варианты по id |
| F09 · удаление способов | anon-DELETE политики не было → тихий `DELETE 0`, UI показывал успех | DELETE-политики добавлены (FK защищает использованные в заказах); чтение справочников для anon открыто полностью — отключённые способы снова видны в админке, их можно включить обратно или удалить |
| F27 · витрина одним RPC | 9 параллельных запросов site.js (очередь соединений) | `draft_storefront_bundle()`: каталог, справочники, тексты, луки, токены брендбука — один round-trip; в бою — прототип `GET /api/storefront` |

## 3. Версия

В `assets/js/config.js` (GitHub-копия) поменять **только строку**
`const SITE_VERSION = '0.13.1-draft';` → `'0.14.0-draft';`.
Ключи базы (`SUPABASE_URL`, `SUPABASE_ANON_KEY`) в GitHub-копии настоящие —
целиком файл не перезаписывать. **Внимание, новый файл:** `assets/js/util.js`
загружается впервые — без него не откроется ни одна страница (он подключён
тегом `<script>` на всех 17 страницах после config.js).

## 4. База, публикация и проверка

1. **Supabase SQL Editor:** выполнить `supabase/16_race_and_integrity_fixes.sql`
   целиком. Скрипт идемпотентен. Правки старых скриптов (02, 07, 09–14) —
   комментарии, префлайты и самопроверка: **объекты БД не меняют, повторный
   прогон не требуется** (но безопасен).
   Самопроверка скрипта 16 должна вернуть:
   `method_delete_policies=2 · methods_readable_all=2 · total_nonneg_constraint=1 ·
   negative_totals=0 · products_in_bundle=8 · content_keys=34 · brand_tokens=20 ·
   reserved_map_fixed=t · set_status_locks=t · create_order_v6=t`.
   DANGER-блок: если в базе были заказы с отрицательным итогом (баг F07),
   их `total` обнулится — это тестовые данные, `negative_totals` в самопроверке
   покажет факт.
2. Загрузить файлы раздела 2 в репозиторий, в config.js править только
   SITE_VERSION. Push в `main` → Pages → на сайте **Ctrl + F5**.
3. **Чек-лист приёмки:**
   - витрина открывается; в DevTools → Network один запрос
     `rpc/draft_storefront_bundle` вместо ~9 REST-запросов (если скрипт 16 не
     выполнен — витрина всё равно работает через запасной путь);
   - заказ с двумя строками одного варианта сверх остатка → читаемое
     «Недостаточно остатка: …», а не сырой код 23514;
   - fixed-промокод больше суммы корзины + комплект → «Итого 0 ₽», заказ
     создаётся (в Table Editor: `total = 0`, не минус);
   - «Управление → Оплата и доставка»: «Удалить» у неиспользуемого способа —
     строка исчезает по-настоящему; у использованного в заказах — сообщение
     «используется в заказах — отключите»; отключённый способ виден в списке
     и включается обратно;
   - «Заказы → Сборка»: подсветка группы строк при наведении работает СРАЗУ
     после открытия страницы (до всяких отгрузок);
   - «Заказы → Список»: карточка заказа показывает историю статусов; при
     ошибке «Отметить оплаченным» кнопка не остаётся заблокированной;
     пустой результат фильтра — строка «Ничего не найдено по фильтрам»;
   - экспорт CSV заказов/статистики/акций/клиентов: имя файла с сегодняшней
     (локальной) датой; значение, начинающееся с `=` (например, имя клиента
     `=cmd|test`), открывается в Excel как текст, а не формула;
   - «Управление → Брендбук»: сохранить новый акцент → «Статистика» с Ctrl+F5
     — графики в новом цвете (палитра из токенов);
   - `login.html?next=https://evil.example` → после входа открывается
     `admin.html`, а не внешний сайт;
   - промокод с минимальной суммой: уменьшить корзину ниже порога → тост
     «Промокод … больше не действует», скидка снята;
   - `python3 tests/check-repo.py` — выход 0.
4. Гонки (F01–F03, F23) проверены разработчиком на живом PostgreSQL 15 двумя
   сессиями: одинарный возврат остатков при двойной отмене, один клиент на два
   параллельных заказа, `used_count ≤ usage_limit`, отсутствие deadlock.
   В Supabase можно смоук-проверить SQL-запросом из двух вкладок SQL Editor
   (одна с `BEGIN; … SELECT pg_sleep(4); COMMIT;`) — сценарии в
   `docs/review-v0131.md`, приложение А.

## 7. Урок для регламента

1. **Расхождение версий функций — реестр.** v5 потеряла join-условие v4
   (`vr.product_id = pr.id`, F12): при `create or replace` функции сверять
   тело с предыдущей версией построчно; расхождения версий заносить в
   реестр «граблей» (этот пункт).
2. **Синтаксис ≠ структура.** `node --check` и check-repo не поймали код,
   вклеенный внутрь чужого колбэка (F10): в чек-лист приёмки волны добавлять
   пункт «проверить фичу СРАЗУ после открытия страницы, до срабатывания соседних
   действий».
3. **Самопроверки обязаны совпадать с фактом** (F19: комментарий «9» при
   фактических 8) — число в комментарии самопроверки сверять прогоном.
4. **Идемпотентность ≠ безопасность повторного прогона для данных** —
   data-миграции (06–08) формально идемпотентны, но затирают правки контента;
   вопрос защиты — F21 (решение ожидается), оговорка внесена в доки.
5. **Гонки проверяются двумя сессиями.** Новые серверные функции, трогающие
   общие строки (остатки, лимиты, дедупликация), тестировать конкурентно до
   публикации волны — сценарий приложения А отчёта ревью.
