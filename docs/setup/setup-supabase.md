# Инструкция 2. Вторая база Supabase и подключение ключей

## Можно ли две независимые базы из одного аккаунта?

**Да.** В Supabase «база» = «проект». В одном аккаунте (и в одной организации)
можно создать несколько проектов, и каждый — это полностью независимый
PostgreSQL со своими таблицами, ключами и RLS: учебный `PaprekolyX` и новый
`Sisku` не пересекутся никак.

Ограничение бесплатного тарифа: **2 активных проекта** на организацию.
У тебя как раз будет два: учебный + черновик Sisku. Если захочется третий —
придётся удалить (pause) один из старых или перейти на платный тариф.
Данные проектов изолированы: ключи от одного проекта не дают доступа к другому.

## Шаг 1. Создать проект

1. Зайти в свой аккаунт https://supabase.com/dashboard.
2. Организацию выбрать **ту же**, где учебный проект (переключатель в шапке).
3. **New project**:
   - Name: `sisku-draft`;
   - Database Password: придумать и **сохранить** (в браузере/менеджере паролей) —
     он нужен только для прямого доступа к БД, сайт работает без него;
   - Region: для черновика любой (например, Frankfurt — ближе к России из
     бесплатных регионов). *Для боевой версии выберем российское решение,
     см. отчёт по проекту, раздел 2.*
4. Дождаться создания (~1–2 минуты).

## Шаг 2. Применить SQL-скрипты

В проекте `sisku-draft`: **SQL Editor → New query**.

**Состав, порядок и назначение скриптов — в реестре `supabase/README.md`**
(единственный источник; обновляется каждой волной — эта инструкция не
дублирует изменчивые данные, решение аналитика 17.10.2026). Кратко:

- **НОВАЯ база:** выполнить по порядку baseline **01 → 02 → 03 → 04 → 05 →
  09** (каждый файл отдельным запросом, Run), затем инкременты при их
  наличии (актуальный состав и порядок — в реестре). Все
  скрипты идемпотентны: повторный запуск ничего не ломает. В конце каждого
  скрипта — самопроверка select'ом: сверьте значения **до символа** с
  ожидаемой строкой из комментария скрипта (строки дублирует реестр
  `supabase/README.md`).
- **ЖИВАЯ база** (`sisku-draft` с контентом владельца): baseline НЕ
  перезапускать (модель F21 — посевы затрут правки); применять только новые
  инкременты в порядке номеров. Одноразовые data-операции в инкрементах
  помечены ⚠ и защищены guard (повторный прогон — no-op, но по регламенту
  выполняются один раз).
- Исторические скрипты (01–25 ревизии до v0.16.0 и инкременты 26–33 волн
  v0.17.0–v0.21.0) — замороженные архивы `supabase/archive/`, НЕ для
  применения; их эффект зашит в baseline ревизии 2 (состояние на v0.21.0).

## Шаг 3. Засеять каталог

Два равнозначных способа — используй **один** из них:

**Способ А (рекомендуемый) — посев скриптом:** в SQL Editor выполни
`supabase/05_seed_catalog.sql` — засеивает каталог без участия CSV-парсера
(6 брендов, 6 категорий, 8 демо-товаров, 20 вариантов, бейдж «New» всем
товарам — v0.21.0; «запасной посев» — урок ошибки «too many fields» при
импорте).

**Способ Б — импорт из бэкапов (Table Editor):** выбрать таблицу → ⋯ →
**Import data from CSV**. Файлы `data/` — автовыгрузки Supabase демо-базы
(06.10.2026; содержат `id` и `created_at` — импортируются в **пустые** таблицы
после скрипта 01). Порядок важен из-за внешних ключей:

1. `data/brands_rows.csv` → таблица `brands`
2. `data/categories_rows.csv` → таблица `categories`
3. `data/products_rows.csv` → таблица `products`
4. `data/product_variants_rows.csv` → таблица `product_variants`

После импорта в Table Editor будет: 6 брендов, 6 категорий, **9 товаров**
(8 демо + тестовый товар владельца, артикул 00001), 20 вариантов.
Справочники и тексты (order_statuses, status_transitions, payment_methods,
delivery_methods, site_content) сеются скриптом 04 — их бэкапы `*_rows.csv`
предназначены для восстановления контента после правок владельца, а не для
первичного посева.

**Примечание (06.10.2026, обновлено 07.10.2026):** в живой демо-базе способ
доставки исправлен владельцем — «Почта России» (код `pochtaruss`), тексты
`site_content` не содержат «Boxberry»; исторически посевы выравнивал скрипт 25
(задача АН-20) — с волны v0.17.0 его эффект зашит в baseline `04` (посев
сразу с `pochtaruss`), сам скрипт 25 — в архиве. Статические fallback-тексты
витрины с волны v0.16.0 — нейтральные, без названий служб доставки. Пути
изображений в бэкапах `data/` — `.webp` после выполнения скрипта 27
(волна v0.17.0, находка B1).

**Если импорт ругается** («too many fields» или сдвиг столбцов): очисти таблицы
(`truncate public.product_variants, public.products, public.categories,
public.brands restart identity;`) и посей каталог способом А.

## Шаг 4. Взять ключи и вставить их в HTML

1. В проекте `sisku-draft`: **Settings → API** (в новом интерфейсе —
   кнопка **Connect** слева → вкладка **API keys**).
2. Скопировать два значения:
   - **Project URL** — вида `https://xyzabcsupabase.co`;
   - **anon public** key — длинная строка, начинается с `eyJ…`.
     Это ПУБЛИЧНЫЙ ключ, его место в коде сайта. Секретный ключ
     (`service_role` / `sb_secret_…`) не копируем никуда: он обходит RLS.
3. Открыть файл **`assets/js/config.js`** (это единственное место, куда
   вставляются ключи) и заменить две строки-заглушки:

```js
const SUPABASE_URL = 'https://ВСТАВЬТЕ-PROJECT-URL.supabase.co';   // ← сюда Project URL
const SUPABASE_ANON_KEY = 'ВСТАВЬТЕ-anon-public-KEY';               // ← сюда anon public
```

4. Сохранить, закоммитить (git push или правка через веб GitHub).
5. Обновить сайт с **Ctrl + F5**: каталог загрузится из базы, тексты
   подставятся из `site_content`.

## Проверка

- Витрина: 8 товаров, фильтры по 6 категориям и 6 брендам, тексты Sisku.
- Оформление тестового заказа → на экране номер заказа; в Table Editor →
  `orders` появилась строка, `product_variants.stock` уменьшился.
- `admin.html`: заказ в списке, смена статуса по модели переходов
  (new → confirmed → packing → shipped → delivered; отмена из new/confirmed),
  отметка оплаты — признак `is_paid`, а не статус (статус «Оплачен» удалён
  в v0.2.0), вкладка «Статистика» с графиками.

## Важные ограничения черновика

- База Supabase находится **вне России**: реальные персональные данные
  покупателей сюда вводить нельзя (152-ФЗ). Только тестовые заказы
  («Тест Тестович», +7 000…). Для боевой версии — российское решение
  из отчёта, раздел 2.
- Админ-панель с мок-авторизацией (v0.4.0+): пароль `123456` написан на
  странице входа `login.html` — войти может любой, кто её открыл. Ссылку на
  админку не публикуем, в индексы поисковиков страницы не попадут (тег
  noindex), но знай: фактически админка открыта всем. Это осознанное
  упрощение макета (SECURITY.md §3).
