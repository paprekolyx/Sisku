## 2. Архитектура

### 2.1. Схема

```
 Браузер пользователя
 │  (HTML/CSS/JS отдаётся как статика; сборка не нужна)
 ▼
 GitHub Pages ──── статический хостинг: 17 HTML-страниц, assets/, data/
 │
 │  supabase-js 2.116.0 (локальный файл assets/vendor/supabase.min.js)
 │  anon-ключ из assets/js/config.js
 ▼
 Supabase (проект sisku-draft)
 ├── PostgREST  — чтение каталога/справочников (RLS: anon-read)
 ├── RPC (plpgsql, security definer) — вся пишущая бизнес-логика:
 │     create_order (v9) · admin_set_status (v4) · admin_set_paid (v2) ·
 │     check_promo (v2) · track_order (v2) · admin_update_client (v0.18.0) ·
 │     draft_admin_bundle · draft_assembly_bundle · draft_reserved_map ·
 │     draft_clients_bundle (v3 — сегменты) · draft_client_card_bundle (v0.18.0) ·
 │     draft_storefront_bundle (v2)
 └── PostgreSQL 15 · 24 таблицы · RLS на всех · 62 политики
```

### 2.2. Принципы (и почему так)

1. **Статика + BaaS, без собственного сервера.** Черновику нужен был быстрый
   способ показать сайт владельцу: GitHub Pages (бесплатно, HTTPS, публикация =
   push) + Supabase (схема, API и функции из коробки). Свой бэкенд на этой
   стадии — лишние дни работы и хостинг; в боевой версии он появится (§14).
2. **Бизнес-логика — в базе, а не в браузере.** Цены, остатки, скидки
   промокодов и комплектов, статусные переходы считаются только серверными
   функциями plpgsql. Браузер физически не может подделать сумму заказа:
   `create_order()` игнорирует присланные суммы и берёт их из БД одной
   транзакцией. Это ключевое решение, перенесённое из учебного проекта.
3. **Ноль сборки, ноль CDN.** Ни npm, ни бандлеров, ни внешних запросов:
   шрифты, supabase-js и Chart.js лежат в репозитории (`assets/vendor/`,
   `assets/fonts/`). Сайт открывается даже при заблокированных CDN и не
   зависит от чужих аптаймов; правка = правка файла.
4. **Контент отделён от кода.** Тексты витрины — таблица `site_content`
   (34 ключа: hero, about, adv, catalog, contacts, footer, order, brand),
   цвета и типографика — таблица `brand_colors`. Владелец правит сайт из
   админки без публикации кода.
5. **Данные воспроизводимы.** Мастер-источники каталога — CSV (`data/`),
   схема и посевы — нумерованные идемпотентные SQL-скрипты (`supabase/01…21`).
   Базу можно потерять и поднять заново за один вечер; бэкапы сверх
   автоматических Supabase не ведутся (осознанно, SECURITY.md §3).

### 3.1. Почему vanilla JS, а не React/Vue/TypeScript

- **Задача черновика — показать дизайн и UX владельцу**, а не построить
  масштабируемое SPA. Сложность интерфейса (17 страниц, модалки, фильтры,
  таблицы с пагинацией) закрыта собственной библиотекой компонентов
  `ui.js`/`ui.css` (кастомные селекты, датапикеры, степперы ±, тосты, drawer,
  скелетоны) — ~9 КБ вместо ~150 КБ фреймворка и toolchain'а к нему.
- **Ноль сборки** = публикация копированием файлов, правки видны после
  Ctrl+F5, нет node_modules,.lock-файлов и риска «не собирается на другой
  машине». Для одного аналитика это решающий фактор скорости итераций
  (12 релизов за проект).
- **TypeScript отклонён** по той же причине: он требует транспиляции.
  Контроль качества вместо типов обеспечивают `tests/check-repo.py`
  (связность id/страниц/ссылок/версий), `node --check` (синтаксис JS)
  и чек-листы приёмки каждой волны.
- **Миграция не блокируется:** транспорт к данным изолирован (страницы ходят
  в БД через небольшие обёртки), поэтому в боевой версии supabase-js
  заменяется на `api.js` с fetch к своему API без переписывания UX.

### 3.2. Почему Supabase (и его границы)

- Даёт за минуты то, на что иначе ушли бы недели: PostgreSQL, REST API
  с RLS, SQL-редактор, Table Editor, бесплатный тариф. Для черновика —
  оптимально.
- **RLS (Row Level Security)** заменил собой серверный ACL: политики
  описывают, что видно анониму (каталог — всё; заказы — чтение, осознанное
  упрощение черновика). Запись — через `security definer` функции.
- **Ограничения, которые приняли knowingly:** проект физически вне РФ
  (→ только тестовые данные, 152-ФЗ); anon-ключ публичен (штатно, защита —
  RLS); бесплатный тариф даёт очередь подключений — 7 параллельных fetch'ей
  админки грузились медленно, проблема решена агрегирующими RPC
  `draft_admin_bundle()` / `draft_assembly_bundle()` (один запрос — один JSON);
  с v0.14.0 и витрина грузится одним RPC `draft_storefront_bundle()`
  (было 9 параллельных запросов — фикс F27 ревью).
- **В боевой версии Supabase выбрасывается полностью** (§14): схема портируется
  в MySQL на российском хостинге, plpgsql-функции — в PHP-сервисы, RLS —
  в серверный ACL-middleware.

### 3.3. Почему GitHub Pages

Бесплатно, HTTPS из коробки, публикация = git push, репозиторий и сайт —
одно целое. Ограничения: нельзя задать HTTP-заголовки (CSP/HSTS — только
в боевой версии), доступность из РФ в 2026 нестабильна (для показа владельцу
достаточно; на этот случай в рабочем каталоге велось зеркало `sisku-pages/`
и архив `sisku-draft.zip` — **решением 05.10.2026 артефакты заморожены**:
не пересобираются и не используются до отдельного указания). Собственный домен черновику не подключали
сознательно — домен появится у боевого сайта.

### 3.4. Почему Python для автотестов

`tests/check-repo.py` (~9 КБ) написан на Python 3 только со стандартной
библиотекой: он запускается где угодно без установки зависимостей
(pglast — опционален, при отсутствии проверка синтаксиса SQL честно
пропускается с пометкой). Альтернатива (JS-тесты) потребовала бы npm —
нарушение принципа «ноль сборки».

### 3.5. Почему будущий бэкенд — PHP 8, а не C#

Решение зафиксировано в `migration-plan.md` (вариант A):

- **Хостинг диктует язык.** Боевой сайт должен ехать на российском shared-
  хостинге (Beget FreeHosting/Start: 1 ГБ, MySQL, постоянный, ~0–420 ₽/мес).
  Shared-хостинги в РФ массово предоставляют LAMP (PHP+MySQL) и почти never —
  .NET; C# потребовал бы VPS с Windows/Linux-администрированием, что дороже
  и сложнее для проекта из одного разработчика.
- **Масштаб задачи.** Магазин с десятками товаров и 10–15 заказами/день —
  типовая нагрузка для PHP+MySQL; запас до платного тарифа — без изменения кода.
- **C# не отброшен навсегда:** API проектируется contract-first (сначала
  контракт эндпоинтов из отчёта, потом реализация), поэтому язык серверной
  части можно заменить, не трогая фронтенд. Вариант B плана — serverless
  Yandex Cloud — тоже рассматривался; выбран A как дешевле и проще в эксплуатации.
- **Что переносится из черновика в PHP почти построчно:** логика
  `create_order`, `admin_set_status`, `admin_set_paid` (plpgsql → PHP-сервисы
  с транзакциями PDO), статусная модель, ключи `site_content`, CSV-мастера.

### 6.2. Статусная модель (Jira-like workflow)

`Новый → Подтверждён → Сборка → Отправлен → Доставлен → Возврат`, из
`Новый/Подтверждён` возможен переход в `Отменён`; с v0.16.0 (скрипт 22)
добавлен переход `Отправлен → Возврат` (заявка на возврат принимается
и из «Отправлен» — менеджер мог ещё не сменить статус). Разрешённые
переходы — таблица `status_transitions`; смена статуса — только через
`admin_set_status()`, которая проверяет переход и пишет историю;
**возврат остатков с v0.16.0 разделён (v4, скрипт 23, фикс F51):
«Отменён» — в продажу (`stock`), «Возврат» — в КАРАНТИН
(`quarantine_qty`, требует осмотра; осмотр — `admin_resolve_quarantine`:
«вернуть в продажу» / «списать»)**; с v0.14.0 (v3, скрипт 16) строка заказа
блокируется `FOR UPDATE` — две параллельные отмены не возвращают остатки
дважды.

**Статусная модель заявок на возврат** (v0.16.0, скрипт 22; черновик до
юриста — ЮР-06/M4): `Заявка оформлена (created) → Товар вернулся на склад
(returned_to_stock) → Товар проверен, возврат оформлен (verified)`,
из `created` и `returned_to_stock` — `Отклонено (rejected)`; `verified`
и `rejected` — финальные (`resolved_at`). Переходы — только через
`admin_set_return_status()`; при «Товар вернулся на склад» заказ
автоматически переводится в «Возврат» (остатки — в карантин). Заявка
создаётся покупателем с витрины — из заказов в статусах «Отправлен» и
«Доставлен» (решение аналитика 06.10.2026; повторные заявки из «Возврата»
не принимаются — антиспам: одна незакрытая заявка на заказ).
Оплата — не статус, а признак `is_paid` + `paid_at` (решение v0.2.0:
заказ может быть оплачен/не оплачен на любом этапе жизненного цикла);
с v0.15.0 (скрипт 18) признак можно менять и у отменённых заказов —
деньги могли поступить после отмены или быть возвращены; статусные
переходы у отменённых по-прежнему заблокированы, событие оплаты пишется
в `order_status_history` с автором.

## 8. Безопасность (кратко; полностью — SECURITY.md)

**Реализовано:** серверный расчёт цен/скидок/остатков (подмена суммы из
браузера невозможна); единая транзакция создания заказа; статусная модель
защищает от бессмысленных переходов; валидация и анти-спам (лимиты, honeypot,
блокировка повторной отправки); экранирование вывода (XSS); `service_role`-ключ
нигде не хранится; маскирование контактов в админке.

**Осознанно отсутствует (границы черновика):** настоящая аутентификация
(мок-пароль 123456 в коде), ролевые ограничения, сессии, 2FA, аудит;
анонимный CRUD каталога (draft-политики 11–14); SHA-256 без соли для
вымышленных администраторов; троттлинг админ-действий; HTTP-заголовки
безопасности (CSP/HSTS — GitHub Pages не даёт); база вне РФ; финальные
юридические документы и чекбоксы согласий. **Перевод в боевой режим без
устранения этого списка не допускается.**

## 11. Производительность и эксплуатационные заметки

- Агрегирующие RPC (`draft_admin_bundle`, `draft_assembly_bundle`,
  `draft_clients_bundle`, с v0.14.0 — `draft_storefront_bundle` для витрины)
  вместо 7–9 параллельных запросов — страницы открываются одним round-trip
  (лечение очереди подключений бесплатного Supabase).
- Все ассеты локальные: шрифты woff2 (кириллические подмножества), vendor-JS,
  изображения — нет запросов к внешним доменам.
- Тема применяется до первой отрисовки (инлайн-скрипт) — нет «моргания»;
  скорость применения токенов брендбука измеряется (`sisku_theme_apply_ms`).
- Ключи дней в графиках — по локальной дате (UTC `toISOString()` давал
  фантомный предыдущий день — исправлено в v0.7.0).
- Скелетоны на время загрузки; при незаполненных ключах БД страницы показывают
  понятную плашку вместо бесконечного скелетона (с v0.17.0 плашка и при сетевой
  ошибке кнопки «Обновить» в админке — находка D2 внешнего ревью).
- Изображения — WebP (v0.17.0, находка B1): hero 1600px q82 (115/151 КБ),
  товары 1200px q82 (26–146 КБ); итог `assets/img/` 0.86 МБ вместо 48 МБ;
  hero — `width/height/fetchpriority=high` (CLS/LCP), «О магазине» — lazy.
- Точечные обновления состояния в админке (v0.17.0, находка B2): смена
  статуса/оплаты не перезагружает `draft_admin_bundle` — правка заказа в state
  + один лёгкий запрос истории + локальный перерендер; `itemsOf()` — индекс
  вместо O(N²) (B3); `stubSrc()` кэшируется (B4).
- **Регламент времени (v0.17.0, находка C1 — решение владельца «локальное
  время»):** моменты — `timestamptz` (UTC в базе); календарные границы (даты
  промокодов) — Europe/Moscow (`check_promo` v2); относительные окна
  (анти-спам 3/10 мин) — интервалы, от пояса не зависят; фронтенд — локальная

## 12. Известные ограничения черновика

1. Мок-авторизация и отсутствие ролей/сессий/аудита (§8).
2. Анонимный CRUD каталога и справочников (draft-политики).
3. Фото — AI-заглушки, черновая загрузка — dataURL в БД.
4. База вне РФ → только тестовые данные; юридические страницы — шаблоны
   с плейсхолдерами; чекбокс согласия в форме заказа есть (v0.15.0), но это
   макет — факт согласия не пишется в БД (боевая реализация — M4, П16).
5. Нет онлайн-оплаты (схема «перевод + кнопка оплачено вручную»),
   нет уведомлений (e-mail/SMS/Telegram), нет интеграций со службами доставки.
6. Нет SEO-разметки, аналитики, защитных HTTP-заголовков, домена.
7. В карточке клиента нет детальной истории заказов (агрегаты считаются
   с v0.13.0; история — предложение №1 в `docs/feature-proposals.md`, волна
   v0.18.0 после сдвига плана).
9. `used_count` промокода не возвращается при отмене/возврате заказа —
   задокументированное решение (внешний ревью 06.10.2026, находка C2;
   комментарий владельца): лимит использований — маркетинговая защита,
   возврат счётчика позволил бы накрутку циклами «заказ → отмена».
10. Магические id/code статусов в SQL (находка D3) — отложено до порта M1
   (единая конвенция кодов, migration-plan §5.1 п. 20); EXECUTE на админ-RPC
   открыт anon — явное решение до боевой M2 (находка A2, §5.1 п. 18).
8. Возвраты (v0.16.0) — черновой контур: фото заявок — заглушка до
   подключения файлового хранилища (M5); обмен не реализуется (только
   возврат; решение — за аналитиком, кандидат v0.17.0+/боевая версия);
   юридические формулировки условий возврата и чека возврата — нейтральные
   до юрблока M4 (ЮР-03/ЮР-06); карантин — счётчик `quarantine_qty`,
   складские движения с журналом — fp №3b (v0.29.0).

отложен; юрблок — отложен до старта боевой среды (гейт M4); хостинг — Beget
free; контент (название/тексты/контакты/каталог/фото) владелец наполняет сам
из админки; логотип — отрисовать с нуля (согласование аналитик + владелец). Главный принцип: **дизайн и UX
черновика не переизобретаются** — меняются слой данных и доступа.

**Переносится как есть:** дизайн-система и темы, UI-компоненты (`ui.js/ui.css`),
шрифты и Chart.js (vendor), разметка страниц, статусная модель и справочники,
механизм `site_content` (ключи 1:1), фронтовая логика витрины и админки
(переписывается только транспорт: supabase-js → fetch к своему API).

**Переписывается:** схема БД Postgres → MySQL 8 РФ (20 таблиц с расширениями;
требуется MySQL 8.0+: JSON, CTE, оконные функции; `key`/`comment`/`value` —
зарезервированные слова MySQL, при портировании переименовать или backticks);
plpgsql-функции `create_order`/`admin_set_status`/`admin_set_paid`/
`draft_save_look` → PHP-сервисы (логика почти построчно); RLS-политики → серверный ACL-middleware (роль из
сессии на каждом эндпоинте).

**Разрабатывается с нуля:** настоящая авторизация (users/sessions/2FA/сброс/
rate-limit/аудит, bcrypt/argon2id); API-слой PHP 8 + PDO (контракт из отчёта);
уведомления (владельцу — e-mail, Telegram исключён решением владельца,
опция ВКонтакте — очень низкий приоритет, не актуальна до запуска боевого
проекта, решение 05.10.2026; покупателям — v1.x: e-mail/SMS; шаблоны
уведомлений управляются из админки); юридический
контур (финальные политика ПДн и оферта, чекбоксы согласий с записью в БД,
сведения о продавце, возврат, cookie-баннер, уведомление Роскомнадзора,
регламент чеков); оплаты (v1 — вручную с регламентом, фаза 2 — эквайринг
ЮKassa); расчёт доставки по API СДЭК/Почта России (**базовый минимум подтверждён
владельцем 06.10.2026; только бесплатные интеграции**, вторая очередь — по
сравнительной таблице `docs/feature-proposals.md` №12; трек-номера — авто при
возможности интеграции, иначе вручную; запуск допустим с ручной отправкой
трека по e-mail);
SEO/мониторинг/бэкап-регламент (Метрика отложена — вместо неё расширение
отчётов админки: деньги по статусам, возвраты, клиенты); боевой контент
(название и тексты — владелец из админки, логотип — отрисовка с нуля,
реальные фото → WebP — владелец загружает после подключения хранилища) —
волна M0/M5.

**Выбрасывается:** Supabase (проект ставится на pause, после переноса
удаляется), `supabase.min.js`, GitHub Pages как боевой хостинг (остаётся
архивом макета с баннером), мок-авторизация, draft-политики anon-CRUD,
AI-фото. Хостинг боя: вариант A — Beget (PHP 8 + MySQL, ~0–420 ₽/мес),
вариант B — serverless Yandex Cloud; репозиторий боевой версии — новый
приватный. Критерии приёмки v1.0.0: HTTPS на своём домене, заголовки
безопасности, Lighthouse Performance ≥85 / Accessibility ≥95, сквозной
сценарий «витрина → заказ → уведомление → статусы → delivered → чек»,
пентест-чеклист авторизации, восстанавливаемый бэкап ≤1 ч.
