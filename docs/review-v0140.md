Волна v0.14.0 выполнена по приложению В основного отчёта **один в один по составу**; все SQL- и JS-фиксы подтверждены живыми тестами на PostgreSQL 15.19 (три гонки, отрицательный total, дубль варианта, фейковое удаление, deadlock-порядок — устранены; идемпотентность 01–16 двойным прогоном сохранена; самопроверки совпали с заявленными; «58 политик» сверено с живой базой). На момент первого прогона верификации волна не принималась по трём расхождениям (V1–V3) + найдена новая регрессия (V4). **После коммитов 4378df2 и f9fa8df расхождения V1–V3 закрыты и перепроверены**; открытыми остаются V4 (регрессия порядка прогонов скриптов 02↔16) и придирки N1–N4 (не блокируют черновик, внесены в чек-лист боевого переноса M1).

### V4 · 🔴 ОТКРЫТО — регрессия при частичном повторном прогоне скриптов 02 после 16

- **Severity:** 🔵 мелкая для черновика (сценарий — ручной частичный повтор), 🟡 для боевого переноса (паттерн «миграция откатывает миграцию»).
- **Где:** `supabase/02_rls_and_access.sql:73–79` ↔ `supabase/16_race_and_integrity_fixes.sql` (блок 5).
- **Суть (воспроизведена на живой базе 04.10.2026):** скрипт 16 расширяет чтение `payment_methods`/`delivery_methods` для anon до `using (true)` — это часть фикса F09 (отключённый способ должен быть виден в админке, чтобы его можно было включить обратно или удалить). Скрипт 02 по-прежнему создаёт те же политики с `using (is_active = true)`. Полный прогон 01→16 сходится корректно (16 выполняется последним), **но повторный прогон одного 02 после 16 молча откатывает расширение**:
  ```
  до:  anon_read_payment_methods | qual = true
  прогон 02 → после: anon_read_payment_methods | qual = (is_active = true)
  ```
  Следствие: отключённые способы снова невидимы в «Управление → Оплата и доставка», кнопки «включить/удалить» для них ломаются (UPDATE 0 / DELETE 0) — частично регрессирует F09. Формально нарушен контракт реестра: «скрипты идемпотентны, повторный запуск безопасен».
- **Статус на 04.10.2026:** НЕ исправлено (подтверждено grep'ом после коммита f9fa8df: в 02 по-прежнему `using (is_active = true)`).
- **Рекомендация (5 минут):** перенести расширение в скрипт 02 — `using (true)` для обеих политик чтения справочников + комментарий «v0.14.0, фикс F09: админка управляет и отключёнными способами; граница — create_order() и витрина используют только активные (проверяется на сервере)». В 16 блок 5 можно оставить как есть (drop/create идемпотентен) или сократить до delete-политик. Альтернатива-минимум: предупреждение в шапке 02 и в supabase/README «после выполнения 16 скрипт 02 повторно не запускать» — хуже, т.к. оставляет две истины.
- **Проверка закрытия (когда будет сделано):** прогнать 01→16 на чистой базе; затем повторно один 02; `select policyname, qual from pg_policies where tablename in ('payment_methods','delivery_methods') and policyname like 'anon_read%'` — qual должен остаться `true`; админка manage.html показывает отключённый способ.

### N1 · 🔴 ОТКРЫТО (📝 перенести в чек-лист M1) — safeUrl пропускает схемы с управляющими символами

- **Где:** `assets/js/util.js`, `safeUrl()`.
- **Суть (проверено node-прогоном):** `'java\tscript:alert(1)'` не матчит ни whitelist схем, ни blacklist прочих схем (tab разрывает паттерн `^[A-Za-z][A-Za-z0-9+.-]*:`) и возвращается как «относительный путь»; браузеры при резолве URL вырезают TAB/LF/CR → в href попадает исполняемый `javascript:`. Аналогично с `\u0000`. Для черновика риск в границах задокументированного anon-CRUD (кто пишет site_content — тот может и хуже); для боевой версии (site_content/messenger_url редактирует админ) — defense-in-depth обязателен.
- **Рекомендация:** первая строка функции — `s = s.replace(/[\u0000-\u0020]/g, '');` (стрип управляющих символов и пробелов) до проверок схем; тест-кейс `'java\tscript:alert(1)' → ''`.

### N2 · 🔴 ОТКРЫТО — revalidatePromo не вызывается при добавлении товара

- **Где:** `assets/js/site.js`, `addToCart()` (кнопка «В корзину» в карточке товара) и `addLook()` («В корзину целиком»).
- **Суть:** фикс F30 покрывает изменения корзины в drawer'е (±/убрать/очистить), но не добавление: при применённом процентном промокоде сумма скидки в сводке устаревает, пока покупатель не тронет количество в drawer'е. Сервер при отправке всё пересчитает (деньги в безопасности) — расхождение только визуальное, но сводка «Итого» на мгновение врёт.
- **Рекомендация:** `revalidatePromo();` в конец `addToCart` (после `saveCart(); renderCart();`) и в `proceed()` внутри `addLook`.

### N3 · 📝 ЧЕК-ЛИСТ M1 — под блокировкой промокода перепроверяется только лимит

- **Где:** `supabase/16_…sql`, `create_order()` v6, блок промокода.
- **Суть:** `check_promo()` валидирует `is_active`/сроки/минимальную сумму **без блокировки** строки, затем строка блокируется `for update` и перепроверяется только `usage_limit`. Окно — миллисекунды внутри одной транзакции, практически недостижимо; noting для полноты.
- **Рекомендация (при переносе в PHP — там это критичнее):** в `select … for update` перепроверять одним условием `is_active and (valid_until is null or current_date <= valid_until) and (valid_from is null or current_date >= valid_from)`.

### N4 · 📝 ЧЕК-ЛИСТ M1 — клиент без ключей дедупликации

- **Где:** `supabase/16_…sql`, `create_order()` v6, else-ветка создания клиента.
- **Суть:** заказ с телефоном без цифр (например «abc») и без e-mail проходит валидацию RPC (`v_phone is not null`), но `draft_phone_key` даёт null → клиент создаётся без phone_key/email_key → каждый следующий такой заказ плодит нового клиента-«дубликата». Фронтенд формат телефона валидирует, поэтому через витрину недостижимо; через прямой RPC-вызов — достижимо. Существовало и в v5 — не регрессия волны.
- **Рекомендация:** в else-ветке — `raise exception 'Укажите корректный телефон или e-mail для связи'` (в боевом API — серверная валидация формата контакта до создания клиента).
